## §20 delegate_task から Kanban プラットフォームへ

今年4月、Hermes のマルチ Agent 能力は関数1つだけだった。6月には、SQLite で支えられた永続的な Kanban プラットフォーム一式になっていた。§07 では、あなたもすでにそれを使って3枚のカードをリレーで回し終えたはずだ。面白いのは、ソースの中に「これは設計だけ。コアには手を入れるな」と白黒はっきり書かれた宣言が横たわっていて、最終的に着地したものが、その宣言を2倍以上に太らせてしまったことだ。

### 旧版の時代: ツール1つが全財産

4月の初版に戻ると、Hermes のマルチ Agent の章は実のところかなり薄かった。プリミティブは1つだけで、`delegate_task` という。

仕組みは分かりやすい。親 Agent が短命なサブ Agent を fork し、タスクを放り投げて、戻ってくるまでブロックして待つ。サブ Agent は隔離されたセッションの中で走り切り、サマリを1段吐いて戻し、それで消える。当時は同時実行は最大3つまで。サブ Agent ごとに違うモデルを使うこともできて、推論には強いモデル、検索には速いモデル、というところまでだった。

（この関数自体も後に育っている。v0.22 ではデフォルトで最大10個のサブ Agent を並行実行でき、バックグラウンドに投げたり、途中で口を挟んで方向を変えたり、止めたりもできる。サブ Agent 単独の上限は250ターンだ。だが本質は変わっていない。1回呼んだら忘れる関数呼び出しのままだ。）

これは標準的な fork-join 構造だ。短くて自己完結した推論のサブタスクには向いている。だが、コミュニティでだんだん当たり前になってきた種類の仕事は支えきれない。数時間走るエンジニアリングのパイプライン、毎朝自動で日報を出すループ、名前を付けて数か月飼いたい永続アシスタント。どれも「1回の API 呼び出しより長く生きるもの」を必要とするが、`delegate_task` にはそれができない。

### 「DESIGN ONLY」と書かれた設計文書

2026年4月25日、Nous Research はリポジトリに1本の PDF を置いた。Hermes Kanban v1 spec だ。私が初めてその扉ページを読んだとき、少し意外だった。

扉ページの Abstract には、数行がきっぱりと書かれている。

> 設計文書原文（扉ページ）: Status: DESIGN ONLY. No implementation accompanies this document. / The kernel requires no changes to run_agent.py, no new core tools.

訳すとこうだ。これは設計だけであり、実装は一切付いてこない。このカーネルは `run_agent.py` を1行も変える必要がなく、新しいコアツールも要らない。

spec 全体の調子が、この潔癖なまでに抑制の利いたミニマリズムだ。カーネルの境界は、物差しで測ったみたいにきっちり引かれている。

| 項目 | v1 設計文書の約束 |
|---|---|
| 状態 | ちょうど6つ: todo / ready / running / blocked / done / archived |
| データベースの表 | 原文に「exactly four tables」、ちょうど4つ |
| 新規コアツール | ゼロ。1つも足してはいけない |
| CLI コマンド | サブコマンド1つ |
| その他 | Skill 1つ、cron ジョブ1つ、それで終わり |

spec の中の dispatcher（ディスパッチャ）も、わざと「愚直」に設計されている。やることは3つだけだ。どのタスクが ready になったかを再計算すること、CAS でアトミックにタスクをクレームすること、worker プロセスを spawn すること。賢いルーティングはしない、予算も見ない、承認もしない。賢い仕事は全部、上位の profile とプラグインに押し付ける。

とても美しい設計だ。問題は、それが自分を抑えきれなかったことだ。

### 反転: 104個の PR が宣言を太らせた

v0.16.0 になって、私は実際に出荷されたコードとこの spec を1項目ずつ突き合わせた。落差が大きくて、少し笑えるほどだった。

> **推奨**
>
> 設計文書の言うこと: 6状態 ・ 4テーブル ・ 新規ツール0 ・ CLI サブコマンド1つ

> **非推奨**
>
> 着地したコード: 9状態 ・ 7テーブル ・ `kanban_*` ツールセット一式 ・ CLI サブコマンド30超（v0.22.2 では第1階層のサブコマンド47個、第2階層まで数えると56本）

どれも突破されている。状態は3つ増えた。triage（人が粗いアイデアを放り込むところ）、scheduled（人を待たず時間を待つタスク）、review（レビューのゲート）だ。表は4つから7つに増え、コアの `tasks` テーブル1つ取っても、列数は十数列から30列前後へ膨れ上がった。

いちばん面子を潰されたのは、あの「no new core tools」の一文だ。実際のコードでは、dispatcher が worker を spawn するたびに、`kanban_show`、`kanban_complete`、`kanban_block` といったツール一式をそのまま worker の schema に詰め込んでいる。これはまさに新しいコアツールではないか。

そのマイルストーンは v0.15.0 で起きた。公式のリリースノート自身が率直に書いている。「Kanban grew into a real multi-agent platform — 104 PRs」。ミニマリズムの設計宣言が、現実の需要に104個の PR で一口ずつ食われて、プラットフォームになってしまった。

> **ポイント**
>
> この「設計文書 vs 着地した実装」の落差そのものが、オープンソースプロジェクトの進化を観察する最良のサンプルの1つだ。それが示すのはこういうことだ。抑制は姿勢としては成り立つが、実際のユーザーの仕事の形は、カーネルの中へ絶えず物を流し込み続ける。「exactly four tables」と書けたチームが、数週間後には、誰かが本気で50個の Instagram アカウントを管理しようとしたせいで、表を7つに増やすことになる。これは設計の失敗ではない。設計が現実と交渉しているのだ。

### delegate_task は死んでいない。格下げされただけだ

こう聞く人もいるだろう。Kanban がこれだけ強いなら、`delegate_task` はもう要らないのでは？

いや、残っている。ソースの中では、Kanban の worker が自分の一回の実行の中では今でも `delegate_task` を呼べることが、繰り返し強調されている。変わったのは、その位置だ。「マルチ Agent の全部」から「関数呼び出し級」のサブ能力へ格下げされ、Kanban が「キュー級」の協働の土台になった。両者は共存し、分業は公式に次の一文で固定されている。

この境界線は覚える価値がある。すっきりしている。

| 項目 | delegate_task | Kanban |
|---|---|---|
| 形態 | RPC 呼び出し（fork → join） | 永続メッセージキュー + 状態機械 |
| 親 Agent | サブ Agent が戻るまでブロック | fire-and-forget、作ったら即 done |
| サブ Agent の身元 | 匿名のサブ Agent、永続する自我なし | 名前付き profile、自分のメモリ／Skill／履歴を持つ |
| 復旧 | なし。失敗は失敗 | block 後に unblock して再実行できる。クラッシュは自動回収 |
| 人の介入 | 不可。全程ヘッドレス | いつでも comment／block／reassign できる |
| タスクあたりの Agent 数 | 1回の呼び出しに1つ | タスクの一生で N 個（リトライ／レビュー／フォローアップ） |
| 監査 | 親のコンテキストが圧縮されれば消える | SQLite の行が永久に残る |

どう選ぶか。公式がくれた判定基準は、暗記するのにうってつけだ。この引き継ぎは、1回の API ループより長く生きて、しかも他の人に見える必要があるか？　必要なら Kanban、不要なら delegate でいい。この一文で、2つのプリミティブの境界がきれいに引ける。

平たく言えばこうだ。`delegate_task` は1回の関数呼び出しで、呼んだら忘れる。Kanban は永続的な作業キューで、引き継ぎのたびに、どの profile（あるいはあなた自身）でも読めて書き換えられるデータが1行残る。

### 「関数」から「インフラ」へ

この反転をつなげて見ると、Hermes のマルチ Agent が4月から6月にたどった進化の道筋は、実ははっきりしている。

> delegate_task（1つの関数） → v1 spec（ミニマリストの宣言） → 104個の PR（太らせる） → Kanban（永続 Kanban プラットフォーム）

SQLite で支えられ、プロセスをまたぎ、単一障害点にも耐える Kanban プラットフォームだ。自動のタスク分解があり、swarm トポロジがあり、定時タスクがあり、タスクごとのモデル上書きがあり、サーキットブレーカー付きリトライがあり、マルチテナントがあり、複数のボードがある。v0.22 ではさらに耐障害性が1層増えた。モデルプロバイダが 429 や 5xx のようなエラーを返したとき、カードはコンテキストを持ったまま再キューされ、失敗したカードはパネル上に worker の最後の出力をそのまま表示する。これらは後の節で1つずつ分解していく。

ただ、この節でまず覚えてほしいのは、この反転そのものだけだ。旧版でいちばん弱かった章が、今では本書全体でいちばん中身のある Part になった。そしてそれがこれほど中身を持てたのは、まさにあの spec が最初から抑制しすぎるほど抑制していたからだ。抑制がきれいなカーネルをくれて、現実がそのカーネルの上にプラットフォーム丸ごと1つを生やしに来た。

次の節ではこのプラットフォームのカーネルに潜り、「愚直」に設計されたあの dispatcher が、どこがどう愚直で、そしてなぜその愚直さこそが本番環境に耐えられる理由なのかを見る。

## §21 愚直なカーネル + ユーザー空間の装飾

複雑そうに見えるマルチ Agent プラットフォームなのに、カーネルは愚直な仕事を3つしかやらない。Hermes は賢いものを全部外へ押し出し、自分は素朴なまでに頑固なスケジューラを守っている。この Unix 的な嗜好こそ、Hermes とあの「プロセス内 Agent 群」との間の、いちばん深い分水嶺だ。

### まず、スケジューラが何をしているか

Kanban システムの心臓は、dispatcher というプロセスだ。名前は大仰だが、実体は cron のようなものだ。一定間隔で目を覚まし、ボードを一巡して、仕事をする。

できる仕事は指折り数えられる。全部で3つだ。

> ready を再計算する → タスクをアトミックにクレームする → worker プロセスを spawn する

ready の再計算とは、どのタスクの前提依存が全部片付いて、着手できるようになったかを見ることだ。アトミックなクレームとは、SQL を1文使ってそのタスクのロックを奪うことだ。`WHERE status='ready' AND claim_lock IS NULL`。データベースの行レベルの競合に頼って、同じタスクをクレームする者が最大でも1人だけ勝つことを保証する。worker の spawn は、実行のための OS プロセスを1つ起動することだ。

これだけだ。以上。

マルチ Agent 協働の華やかな部分、賢いルーティング、予算配分、承認ガバナンス、誰を優先するか、そういったものは dispatcher は一切関知しない。どのタスクが大事かも知らないし、いちばん安いモデルに回すべきか高いモデルに回すべきかも知らないし、worker が2つ喧嘩したらどうするかも気にしない。こうした判断は全部、dispatcher の手の届かない場所へ押し出されている。profile の system prompt の中、ユーザーが入れた plugin の中、カード自身が持つ設定の中だ。

これが「愚直なカーネル」の意味の全部だ。カーネルはメカニズムの正しさだけを保証する（タスクが2つのプロセスに同時にクレームされることはない、死んだ worker は回収される）。一方で戦略、誰に回すか、いくら使うか、人の承認が要るかは、全部ユーザー空間に任せる。メカニズムと戦略の分離は、Unix が50年書き続けてきた古い作法だ。

### なぜわざわざカーネルを愚直にするのか

賢さを外へ押し出すのは、手抜きに聞こえるが、実は抑制の一種だ。

「カーネルが賢すぎる」せいで死んだシステムを、私は見すぎてきた。スケジューラに業務を理解させ始めた瞬間、どのタスクを優先すべきか、予算をどう割るか、いつ人を呼ぶか、それはもう二度と変えられなくなる。新しいシナリオが1つ増えるたびに、いちばん中核で、いちばん触りたくない部分に戻らなければならない。Hermes は逆だ。カーネルは業務知識を持たないほど愚直だから、ほぼ変更が要らない。新しい遊び方を足したければ、ユーザー空間で足す。カーネルは微動だにしない。

面白いのは、Nous がこの哲学を、同世代のあるシステムと対照させていることだ。Google は2026年4月の Gemini Enterprise で、Agent スタックを2つの平面に割った。承認とコンプライアンスを担う「ガバナンス制御平面」と、仕事を担う「速度実行平面」だ。Hermes は意図的に実行平面にだけ留まり、ガバナンスにはカーネルの中では一切触れない。欲しい人は自分で plugin として入れる。大企業が求めるガバナンス一式を選んだ側と、開発者が求めるシンプルさを選んだ側とでは、選択は違うが、どちらも自己完結している。

### swarm: 新しいランタイムを持たない「組み合わせシュガー」

Hermes には、コマンド1つで複数の Agent を立ち上げる `hermes kanban swarm` がある。目標を1つ渡し、役割をいくつか指名すると、協働の網が広がる。数個の専門家 worker が並行して働き、verifier が1つゲートを守り、synthesizer が1つ締める。

初めて見る人は、この裏には専用の swarm エンジンが隠れているはずだと思うだろう。ない。

swarm モジュールは冒頭で自らこう書いている。2つ目のスケジューラは意図的に導入しない。やっていることは、既存の Kanban カーネルの中に、固定の形のタスクグラフを書き込むことだけだ。

> 計画のルートタスク（作ったら即完了） → 並行する専門家 worker → verifier のゲート → synthesizer が締める

その図の中の線はどれも、状態はどれも、ボードがもともと持っているプリミティブだ。fan-out の並行、pipeline の直列、タスク間の依存リンク。worker 同士が情報を共有する「ブラックボード」さえ、新しく作ったストレージではない。ルートタスクの上に付いた構造化 JSON コメントがそれで、後から書いたものが先のものを上書きし、ついでに誰が書いたかも記録する。dashboard も、通知も、コマンドラインも、swarm のために新コードを足す必要のあるコンポーネントは1つもない。新しいものを何も作っていないのだから。

では swarm の本質は何か。fan-out と pipeline とブラックボードという数個の古い材料を混ぜた、組み合わせのシュガーだ。文法の上では、コマンド1つで複雑なトポロジが手に入るのに、下では新しいランタイムは何も走っていない。「カーネルに手を入れない前提で高レベルの能力を1つ足す」ことの、きれいな実例だ。能力を足したければ、ユーザー空間で組み立てる。カーネルの中にエンジンを詰め込まない。

### NanoClaw: 覚えておく価値のある反面教師

ここで反例を1つ招かないと、Hermes がなぜこれほど頑固なのかが見えてこない。

NanoClaw というプロジェクトがある。「プロセス内サブ Agent」に対応した最初の個人アシスタントをうたう。そのマルチ Agent はこう組まれている。team-lead が自分のプロセスの中で、上流 SDK のクエリインターフェースを通じて、サブ Agent を群れで孵化させて仕事を手伝わせる。聞こえは優雅だ。Agent が全部1つのプロセスの中にいて、プロセス間通信の手間が省ける。

問題はライフサイクルに出る。これらのサブ Agent の命は、そのクエリインターフェースの手に握られている。team-lead のその回の呼び出しが終わると、サブ Agent は音もなく殺される。仕事の真っ最中で、ファイルがまだ書き出されていなくてもだ。Nous の設計文書はこの落とし穴を記録していて、一文が特に辛辣だ。成功したように見えて、実際の成果物はファイル0個。

Hermes はこの教訓を、設計文書の見出しに刻んだ。「重要な不変条件: プロセス内サブ Agent 群を作らない」。原話の大意はこうだ。

> 協調する worker はどれも、ユーザーの支配下にある OS プロセスであり、ある SDK のクエリのライフサイクルの中にあるサブ Agent ではない。worker が退出するとき、きれいに退出しても、クラッシュしても、強制終了されても、そのクレーム・ロックは失効し、次の dispatcher のスキャンで、そのタスクは再クレームされる。私たちが所有していないライフサイクルは、1つもない。

この「私たちが所有していないライフサイクルは、1つもない」という一文が、哲学全体の眼目だ。Hermes は、プロセス間通信、ハートビート検出、クラッシュ回収といった重いコストを進んで引き受けても、worker の命を、自分で制御できない上流 SDK には渡そうとしない。

> **推奨**
>
> Hermes: worker はそれぞれ独立した OS プロセス。worker が死んでも（クラッシュ／強制終了／正常退出）、クレーム・ロックは自動で失効し、タスクは再ディスパッチされる。ライフサイクルは完全に自分の支配下にあり、最悪でも再実行が1回で、結果が黙って消えることはない。

> **非推奨**
>
> NanoClaw 式のプロセス内群: サブ Agent の命は上流 SDK のクエリのライフサイクルにぶら下がる。team-lead のその回が終われば、サブ Agent は黙って殺され、途中の仕事はそのまま蒸発する。「成功したように見えて、成果物はゼロ」。

OpenClaw のような、プロセス内 Agent 群を売りにする系統の方案にも、同じ脆弱さがある。プロセス内が必ず間違いだ、と言いたいのではない。言いたいのは、あなたの Agent の生死が、あなたが所有していないライフサイクルに懸かっているなら、時限爆弾を1つ埋めたということだ。Hermes は、見た目にはもっと重く、実はもっと誠実な道を選んだ。境界は OS プロセス、それだけだ。

### では delegate_task はもう要らないのか

ボードがこれだけ強いなら、古い `delegate_task` は捨てるべきか。捨てていない。前の節（§20）で両者の分業は項目ごとに並べた。判定基準は一文だ。この引き継ぎは、1回の API ループより長く生きて、しかも他の人に見える必要があるか？　必要なら Kanban、不要なら `delegate_task` でいい。

ここでは、前の節で細かく言わなかった点を1つだけ補う。両者は重ねて使える。ボードの中のある worker が、自分の一回の実行の内部で、内部の推論のために `delegate_task` を呼ぶことは、今でもできる。関数呼び出しが永続キューの中に埋め込まれ、それぞれが自分の役目を果たす。これはまさにまた「愚直なカーネル」の現れで、Kanban は `delegate_task` を呑み込んだのではなく、その上に永続の外殻を1層足しただけだ。

### この嗜好にはどれだけの値打ちがあるか

振り返ると、Hermes のこの「愚直なカーネル + ユーザー空間の装飾」が節約したのは、コードの量だけではない。

節約したのは、将来の変更コストだ。カーネルが愚直だということは、それが安定しているということであり、swarm を足すにも、新しい協働パターンを足すにも、新しいコスト管理の戦略を足すにも、いちばん中核の部分に戻る必要がないということだ。賢いものはユーザー空間に生きていて、壊れても、古くなっても、替えたくなっても、いつでも替えられる。カーネルは見なかったことにする。

もっと深い層では、節約したのはライフサイクルへの支配を失うリスクだ。「worker はどれも私が所有する OS プロセス」という原則を守るのは、見た目には重い。引き換えに得られるのは、最悪の場合でも再実行が1回で済むことであって、NanoClaw のような音のないゼロ化ではない。複雑さを外へ押し出し、境界を固く守るカーネルは、何でも先回りして考えてくれる賢いカーネルよりも、たいてい長生きする。

次の節ではこの土台を実際に使って、8つの協働パターンがこの数個の愚直なプリミティブからどう生えてくるのか、そしてマルチ Agent のコストをカードごとにどうきっちり計算するのかを見る。
## §22 8つの協働パターンとカード単位のコスト管理

前の節で、Kanban のあの「愚直なカーネル」の正体が分かった。この節では地面に降りる。同じ tasks + links + comments の一式から、まったく異なる8つのマルチ Agent 協働の形が組み上がる。もっと面白いのは、カードごとにモデルを1つ固定できることで、マルチ Agent のコスト管理が、最後には1枚1枚のカードの上に落ちてきたことだ。

### 新しいプリミティブはない。あるのは新しい組み合わせだけ

ここまで読むと、こう予想するかもしれない。8つの協働パターンを語るなら、底には8組の仕組みが要るのでは？

ちょうど逆だ。Hermes の設計文書はこの8つのパターンを P1 から P8 と呼び、どれも同じ部品一式から組み上がっている。タスク、タスク間の依存リンク、タスク上のコメント、誰が担当するか（assignee）、どのワークスペースで走るか。「投票」のために投票エンジンを作ることも、「パイプライン」のためにパイプラインエンジンを作ることもしていない。

この設計でいちばん学ぶ価値があるのは、まさにここだと私は思う。マルチ Agent システムを設計する人の多くは、シナリオ1つに新機能1つを割り当てる癖があって、最後には誰にも保守できないほどシステムが膨れる。Hermes は逆で、まずプリミティブを最小まで圧縮し、それから組み合わせでシナリオをカバーする。

まず8つのパターンを並べる。一目で、自分の欲しい形が見つかるはずだ。

| 番号 | パターン | 形 | 典型的な用途 |
|---|---|---|---|
| P1 | Fan-out（扇状展開） | 同じ担当者、依存のない兄弟タスクが N 個、並行実行 | 一括処理: 50個のファイルを一度にレビュー |
| P2 | Pipeline（パイプライン） | 役割特化のチェーン、順番にリンク | 調査 → 編集 → 執筆、それぞれの専門で |
| P3 | Voting（投票／法定数） | 同じ課題に担当者の異なる N 個 + 集約役1つ | 複数の案を出してから最良を選び、統合 |
| P4 | Long-running journal（長期ジャーナル） | 同じ担当者 + 同じ共有ディレクトリ + 繰り返しタスク | 日報・週報、日をまたいで同じ置き場に蓄積 |
| P5 | Human-in-the-loop（人がループの中） | ブロック → 質問 → 人が回答 → 解除 → 再実行 | 判断の付かない所で止まって、あなたの決定を待つ |
| P6 | @mention 委任 | メッセージの中で profile を @ すると、自動でカードを作って割り当て | 会話のついでに、仕事をある Agent に放る |
| P7 | Thread-scoped（スレッド単位のワークスペース） | ワークスペースを現在の会話のあるディレクトリに固定 | このプロジェクトの仕事は、このプロジェクトの中でやる |
| P8 | Fleet farming（フリートファーミング） | 専門家 profile 1つ + 並行タスク N 個 + 対象ごとにディレクトリ1つ | 1つの Agent が50アカウントを管理 |

8つの中で特に取り上げて語りたいのは P1、P3、P8 だ。新人が陥る罠をいちばん露わにするからだ。

### P1 扇状展開: 並行は「プロセス内分身」ではない

Fan-out はいちばん簡単に聞こえる。大きな仕事を N 個に切って、同時に走らせる。だがここに、Hermes と同種のシステム多くの根本的な分岐が隠れている。前の節（§21）の「プロセス内分身 vs 独立した OS プロセス」という、あの問題だ。プロセス内分身の命はメイン Agent にぶら下がっていて、メイン Agent が終われば黙って殺され、仕事が途中でも同じように蒸発する。

Hermes の P1 はそうしない。扇状に広げたタスクはどれも、独立した OS プロセスだ。スケジューラは N 個のタスク全部をアトミックにクレームし、本物のプロセスを N 個 spawn する。互いに依存せず、1つが落ちても他に影響はなく、落ちたものは再クレームされて、もう一度走らせることさえできる。

要点はこうだ。「並行」には2つの生え方がある。1つはプロセス内分身（壊れやすく、上流 SDK のライフサイクルに依存する）。もう1つは、それぞれ独立した OS プロセス（落ちても復旧でき、終われば監査できる）。Hermes は徹頭徹尾、後者を選ぶ。これは前の節の「愚直なカーネル」の哲学が、協働の層にまで続いているものだ。

### P3 投票: 数個の Agent に喧嘩させてから、1つに裁定させる

P3 の形は優雅だ。N 個の Agent が同じタスク記述を受け取るが、担当者は違う（違うモデルでも、違う profile でもよい）。それぞれ独立に答えを1つ作る。そこへ集約タスクが1つあって、この N 個のタスクからリンクされ、数個の答えを並べて、1つを選ぶか、1つに統合する。

この手は「1回では正解に届かないかもしれない」タスクに特によく効く。例えば3つの Agent に案を1版ずつ書かせ、4つ目をレビュアーにする。1つの Agent がうつむいて1版書くより、ずっと安定する。

ついでに、Hermes 内蔵の高レベルの包みが1つある。swarm だ。前の節で言ったとおり、`hermes kanban swarm` の下には2つ目のスケジューラはなく、P1 の扇状展開と pipeline と共有ブラックボードを組み合わせた「組み合わせシュガー」にすぎない。コマンド1つで「並行する専門家 + ゲートを守る検証者 + 締める統合者」という陣形を引き出せる。検証者は、証拠が十分なときにだけ通し、足りなければ、不足しているものを明記してカードを差し戻す。

### P8 フリートファーミング: 1つの Agent が50アカウントを回す

P8 は設計文書の中の目玉の実例で、「このために専用ツールを作るな」がいちばんよく分かる例でもある。

50個のソーシャルアカウントを管理するとする。数時間ごとに、それぞれ1巡の保守を回す。従来の発想なら、たぶん RPA ツールを探して、フローを山ほど設定することになるだろう。Hermes のやり方はこうだ。専門家 profile が1つ、並行タスクが N 個、アカウントごとに独立したワークスペースディレクトリが1つ、定時タスクが一定間隔でアカウントごとにカードを1枚作る。

> insta-manager profile 1つ → cron が巡回ごとにアカウント単位でカードを作成 → アカウントごとに独立したワークスペース → 失敗はクレーム・ロックの期限切れで自動回収

どのアカウントのその巡回が落ちても、そのクレーム・ロックは時間切れで失効し、次の巡回で自動的に再クレームされて再実行される。アカウントごとの履歴はタスクのイベントログに残り、監査できる。設計文書に、私の好きな一文がある。これは RPA の形をしたワークフローだが、RPA ツールは使わない。専用インフラがないことこそがその特性であって、欠陥ではない。

### カードにモデルを固定する: コスト管理は最も細かい粒度に落ちる

協働の形を語り終えたので、お金の話をしよう。マルチ Agent が走り出すと、トークン消費は単一 Agent の何倍にもなる。これは現実の痛点だ。

4月の Hermes でも「サブ Agent ごとに違うモデル」はできたが、それは親 Agent が委任のときに一括で決め打ちするものだった。今はもっと細かい粒度に上がっている。カード1枚ごとに、自分がどのモデルで走るかを独立に指定できる。

タスクの表で言えば、`model_override` というフィールドが1つある。スケジューラがそのタスクの worker プロセスを spawn するとき、カードにモデルが固定されていれば、コマンドラインに `-m` を付けて一緒に渡す。その後、カードには `provider_override` と `reasoning_effort` のフィールドも増えた。どのプロバイダを使うか、推論をどれだけ深くするかまで、カード1枚ごとに決められる。

> **推奨**
>
> 定型コードを書く、フォーマットを回す、単純な分類をする → 安くて速いモデルを固定し、お金と時間を節約

> **非推奨**
>
> 難物に取り組む、肝心の推論をする、中核の案を書く → 高くて強いモデルを固定し、使うべきお金は使う

公式の原話は「安いモデルに定型の仕事をさせ、高いモデルに難しいサブタスクをさせる」だ。この言葉の裏には、とても現実的な勘定がある。十数枚のカードからなるワークフローで、本当に最上位のモデルが要るのは2、3枚だけかもしれない。残りは安いモデルで十分に走る。マルチ Agent の経済学は最後、あなたがカード1枚ごとにモデルを調整する手間を惜しむかどうかに落ちてくる。

> **ポイント**
>
> 自分の Agent チームを設計するとき、最初から全カードに最強モデルを載せようと急がないこと。タスクを「難易度」で一巡仕分けし、定型の仕事と検索の仕事は安いモデルに任せ、最上位の枠は本当に推論を食う工程のために残す。頻繁に走るワークフローでは、この差額は積もると相当なものになる。

### goal_mode: Ralph ループをカーネルに取り込んだ

もう1つ、私が気が利いていると思う能力がある。`goal_mode` だ。

Agent を触ったことのある人なら、Ralph というテクニックを聞いたことがあるかもしれない。Agent に同じ目標を繰り返し走らせ、1巡ごとに到達したかどうかを確認し、届いていなければ続けて走らせ、片付くまで回す。以前は、これを外側に自分でループを組まなければならなかった。

Hermes はそれを、カードの上のスイッチにした。カードが `goal_mode` を開くと、1巡走り終えるたびに、補助の判定役がその巡回の成果物とカードのタイトル・本文を突き合わせ、未完了なら続きを書くためのプロンプトを同じセッションに送り返して、走らせ続ける。判定役がうなずくか、巡回数の予算（デフォルト20巡）を使い果たすまでだ。

これは前の節のあの発想の、もう1つの実例だ。Ralph は独立したランタイムにはならず、カードに取り込まれて、1つのフィールドになった。使いたければ開く。使わなければ、存在しないも同然だ。

### 横への拡張: 複数ボード、マルチテナント、複数 Gateway

最後に規模の話をしよう。あなたの Agent チームが「数枚のカード」から「数本の事業ライン」に育つと、Hermes は3層の隔離手段をくれる。粒度は粗いものから細かいものへ。

| 層 | 隔離の強さ | 使い方 | どんなとき |
|---|---|---|---|
| 複数ボード（Boards） | ハードな境界 | ボードごとに独立したデータベース + ワークスペースディレクトリ + スケジュールの視点 | 事業を完全に分け家し、互いに見えないようにする |
| マルチテナント（Tenant） | ソフトな名前空間 | ボード内の tenant ラベル1つでソフトにフィルタ | 専門家チーム1つが複数の事業を担当する |
| 複数 Gateway | プロセス級 | 6月: 複数の Gateway が並行し、スケジューラを持つのは1つだけ。v0.22: デフォルトで1つの Gateway が全 profile を担当 | profile ごとに別々に走らせ、負荷を分散する |

公式の一文が、最初の2層の関係を言い切っている。テナントはソフトなフィルタであり、ボードこそがハードな隔離境界だ。同じ専門家 fleet が、違う tenant ラベルで複数の事業を担当し、ワークスペースのパスとメモリの接頭辞でデータを隔てる。本当に完全に分け家して、誰にも誰も見せたくなければ、ボードを2つ開く。

複数 Gateway の層には、踏みやすい落とし穴が1つある。Gateway プロセスは複数同時に走らせられるが、スケジューラを持てるのは1つだけで、残りは自分のスケジュールを切らなければならない。理由は複雑ではない。複数のプロセスが同時に同じ SQLite 接続を奪い合えば、読み書きの競合が増幅するからだ。「カーネルは愚直なまま、拡張性は組み合わせで」というこの選択は、この層でも一貫している。

v0.22 ではこの層はさらに一段シンプルになった。デフォルトでは1台のマシンで Gateway は1つだけ走り、全 profile がその上にぶら下がる（旧来のユーザーは `hermes gateway migrate --multiplex` で移行する）。「誰がスケジューラを持つか」という問題は、大半のシナリオでは自然に消えた。本当に複数マシンにまたがって走らせるなら、公式が複数 Gateway の文書を別に用意している。

### 1つの問いに戻る: 自分のチームをどう設計すべきか

この節をつなげると、実はそのまま埋めていける設計チェックリストになる。

まず形を問う。あなたの仕事は一括並行（P1）か、順序のあるパイプライン（P2）か、複数案の投票が要る（P3）か、長期に日をまたいで蓄積する（P4）か。次に人と機械の境界を問う。どのステップで止まって、あなたの決定を待つべきか（P5）。それからコストを問う。どのカードに安いモデルを使い、どのカードに最上位の価値があるか。最後に規模を問う。ボードを複数開いて、事業を分け家する必要があるか。

この一式で私がいちばん感心するのは、新しい概念を山ほど学ばせてこないことだ。8つのパターン、カード単位のコスト管理、横への拡張、その底にあるのは、前の節のあの愚直なカーネルのままだ。タスク、リンク、コメント、担当者、ワークスペース。チームを設計するというのは、本質的には、この数個の部品の並べ替えでしかない。

次の節では協働の層を離れて、Hermes 自身がどこにインストールされ、これらのプロセスのコマンドがどのマシンに落ちるのかを見る。これだけの並行プロセスを放った以上、この話は避けて通れない。
