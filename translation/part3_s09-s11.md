## §09 造る、直す、続ける：自己改善の3台のエンジン

初版に書いたのは「手綱は自分で育つ」という一文だった。その後ソースコードを読むようになって、今では指さして言えるようになった。この手綱を誰が育てているのか、育ち方がずれたら誰が剪定するのか、切り間違えたらどう救うのか。それは一つの理念から、バックグラウンドで動き、それぞれ担当を持つ3台のエンジンへと変わっていた。

### まず、初版で残した宿題から

前版の Hermes 橙皮書で学習ループについて書いたとき、対応するバージョンは v0.7.0 だった。当時の私の言い方はかなり曖昧で、「メモリを書き、Skill を作る Agent」という程度のものだった。自己進化するとは言えても、「具体的にどのファイルが、どの条件で発動し、どのスレッドで動くのか」と問われれば、答えられなかった。その頃のそれは本質的にはまだ理念であり、プロンプトに促されて何かを保存するメイン Agent が一つあるだけだった。

2か月後、それは8つのバージョンを跳び越えて v0.16.0 になった。私はソースコードを1行ずつ読んで、その理念の一式が実体のあるインフラとして工学的に実装されていることを発見した。今版の v0.22.2 では骨格は変わらず、細部がかなり変わっている。以下、該当箇所ではその都度明示する。最もすっきりした分け方は、3つの動詞である。造る、直す、続ける。

```
造（Background Review）→ 修（Curator）→ 続（Goals / Ralph Loop）
```

「造」は、会話のたびにサブ Agent を静かにフォークして振り返りをさせ、今回何を学んだか、それをどの Skill に書くかを決めること。「修」は、7日に一度だけ目を覚ます保守担当で、Agent が作った Skill のライブラリに剪定とアーカイブを行うこと（似た Skill を統合する工程は、今はデフォルトでオフになっている）。「続」は、目標が未達成のとき、Agent が自分で処理を継続し、1回の返答で止まらずに何ターンも走り続けること。

3台のエンジンは、まったく異なる3種類の時間スケールで動いている。この節ではまず3台それぞれの位置づけを整理し、続く2節で、特に面白い2台を掘り下げる。

### 自己進化するものは、自己整理もできなければならない

エンジンを分解する前に、この仕組みを見るための角度を一つ渡しておきたい。そうしないと、小さなバックグラウンドタスクの寄せ集めに見えてしまう。

自分で Skill を育てる Agent には、避けられない副作用がある。新しい問題を解くたびに経験を1件保存したくなり、数か月も走らせれば、狭くて重複した Skill が何十、何百と溜まる。どれも当時のあの1件のバグにしか使えず、全部合わせればカタログを汚染し、トークンを無駄に燃やすゴミの山だ。増えるだけで減らないシステムは、最後には必ず自ら膨れ上がって潰れる。

だから Hermes のこの仕組みが本当に成立しているのは、それが「造れる」ことではなく、造ると同時に整理の仕組みを備えていることにある。ソースコードを読んでいるときに頭に浮かんだ比喩は、生物の細胞だった。増殖もすれば、アポトーシス（計画的に死ぬこと）もする。増殖が組織を成長させ、アポトーシスが老化した細胞、間違った細胞、不要な細胞を取り除く。増えるだけで死なない組織には名前がある。腫瘍だ。Hermes の Background Review が増殖を担い、Curator がアポトーシスを担う。この2つは対になる一組であり、セットで現れる。

この角度を持てば、3台のエンジンはすんなり見えてくる。

### 第1のエンジン「造」：会話のたびに行うバックグラウンドの振り返り

このエンジンに対応するソースコードは `agent/background_review.py` だ。その動き方は、ファイル冒頭のコメントが率直に書いている。会話のターンが終わるたびに、メイン Agent はバックグラウンドスレッドをフォークし、直前の会話のスナップショットを再生して、自らに問いかける。今回、Skill やメモリに保存したり、書き換えたりする価値のあるものはあったか。

肝心なのは、それがメインの返答を送り出した後に動くことだ。v0.18 以降は、もう一段コストも削られている。振り返りは補助モデルが担当し、要約された文脈を見て行い、頻度も状況に応じて自ら調整する。ソースコードのコメントはその理由をわざわざ説明している。振り返りは、ユーザーのタスクとモデルの注意を奪い合っては決してならない。だからこれはベストエフォート（最善は尽くすが、失敗しても構わない方式）であり、失敗すれば静かにスキップし、メインの処理を決して引きずらない。あなたが会話しているとき、背後で分身がメモを取っていることなど、まったく感じないはずだ。

それを発動させるのはカウンタが1つではなく2つあり、しかも両者はずらしてある。この細部は、設計者が「知識には2種類ある」と考え抜いていることの表れだと私は思う。

| カウンタ | 何を数えるか | デフォルトの閾値 | 対象の知識 |
|---|---|---|---|
| メモリナッジ | 会話のターン数 | 10ターンごと | あなたが誰で、今何をしているか |
| Skill ナッジ | そのターンでのツール実行回数 | 10回ごと | この種の仕事をどう進めるか |

なぜメモリは「ターン」で、Skill は「ツール実行回数」で測るのか。少し考えてみると、その理屈はなかなか微妙だ。複雑なタスクは、会話の上では1、2往復しかなくても、内部では何十回もツールを実行していることがある。そういう仕事ほど、「この種のことをどうやるか」という手続き的な知識が蓄積しやすい。だからツール実行回数をものさしにするのが妥当なのだ。メモリは「あなたが誰か」、Skill は「仕事をどうやるか」。2種類の知識を、2本のものさしで測る。どちらの閾値も設定で変更できる（メモリ側は `memory.nudge_interval` で、デフォルトはやはり10）。v0.22 ではさらに一歩緩められ、バックグラウンドの振り返りは今やどの Skill でも書き換えられるようになり、学んだことはそのタスクに関連する Skill に書き込まれる。

このエンジンで最も引用に値するのは、Skill を振り返るときに使うプロンプトである。核になる数条を抜き出すと、これはほとんど「AI は自分にどうルールを書くべきか」という工学的な方法論そのものだ。

デフォルトで学ぶべきだ、とされている。プロンプトの原文はこうだ。「Be ACTIVE（積極的であれ）。ほとんどのセッションでは、少なくとも1回は Skill の更新が生まれるべきだ……何もしない振り返りは、学習の機会を逃したのであって、中立的な結果ではない」。それは「学ばないこと」を安全なデフォルトではなく、職務の放棄として定義している。

もっと面白いのは、学習シグナルの定義である。Mitchell Hashimoto が Claude Code を使うときの習慣として、Agent が間違えるたびに `CLAUDE.md` にルールを1条追加するというものがある。Hermes はこれを自動化し、しかも「間違い」をユーザーの不満な口調として具体化した。「Xはやめて」「長すぎる」「そういう並べ方をしないで」「なんでまた説明してるの」「答えだけ言って」。こうした苛立ちのシグナルが一級の学習シグナルとして列挙され、その場で Skill の中に注意点や手順をルールとして書き込むよう求められる。

Skill の直し方にも優先順位があり、何かあればすぐ新規作成とはならない。まずそのターンで読み込んだばかりの Skill を直し、次に既存の大きなカテゴリを直し、次にそのカテゴリの下にサブファイルを追加し、対応するカテゴリが本当にない場合にだけ新規作成する。この優先順位は、Skill が際限なく膨らむのを防ぐためのものだ。古いものにパッチを当てられるなら、新しいものは作るな、ということである。新規に作る Skill の名前も「クラス単位」でなければならず、特定の PR 番号、特定のエラーメッセージ、今日だけの仮称で命名することは禁止されている。ソースコードの原文はかなり厳しい。その名前が今日のこのタスクにしか意味を持たないなら、その名前は間違っている、というのだ。

### 第2のエンジン「修」：Curator、7日に一度目覚める保守担当

第2のエンジンは Curator で、ソースコードは `agent/curator.py` にある。これは旧版の本にはまったく存在しなかった。v0.12.0 で生まれ、その版は公式にそのまま「The Curator release」と名付けられ、リリースノートの1行目はこうだった。Hermes は今や、自分で自分を保守できるようになった。

それがやるのは、上で言った「アポトーシス」の側、つまり Agent が自作した Skill のライブラリへの剪定とアーカイブである。純粋な保守であり、新しいことは学ばない。

バックグラウンドの振り返りは、振り返りの最中に2つの Skill の重なりを見つけても、自分では統合しない。「メモを1件残し、大規模な処理は Curator に任せる」だけだ。2台のエンジンの作業は、ソースコードの中で明確に切り分けられている。

Curator の発動リズムは第1のエンジンとまったく違う。cron のバックグラウンドプロセスに頼るのではなく、アイドル検出に頼っている。デフォルトでは最大で7日に1回、そして Agent が2時間アイドル状態になって初めて動く。もう一つ、気が利いた関門がある。新規インストール直後やアップデート直後の最初のティック（定期チェック）では、あなたの Skill ライブラリにすぐには手を付けない。「前回の実行時刻」を「今」として記録し、丸1周期が経つまで本当には動かないのだ。設計者の配慮はこうだ。アップデートが終わった直後にユーザーのライブラリを大きくいじるのは、あまりに唐突すぎる。

その作業は2段階に分かれ、第1段階では大規模モデルをまったく使わない。純粋な関数の状態マシンが、各 Skill の「最終活動時刻」に基づいてライフサイクルを機械的に進める。

```
active（有効） ―14日使われない→ stale（陳腐化） ―30日使われない→ archived（アーカイブ済み）
```

陳腐化した Skill は、再び使われれば自動的に active（有効）へ復活する。pin（固定）された Skill は自動的な遷移に決して参加しない。この段階はトークンを1円も燃やさず、タイムスタンプだけで進む。（この2つの閾値は、6月の v0.16 ではまだ30日と90日で、後に14日と30日に引き締められた。§06 の `hermes curator status` の画面に出ているのがこの数字だ。）第2段階が大規模モデルによる振り返りで、Agent をフォークして、どれを統合すべきかを実際に判断する。ただし v0.17 以降、この第2段階はデフォルトでオフになっている。理由はトークンの節約だ。有効にしたい場合は、設定で `curator.consolidate: true` とするか、手動で `hermes curator run --consolidate` を実行する。

Curator は3台の中で最も細部が多く、ブレーキも最も重く作られている。本書では次節を丸ごとこの1台に充てる。そこでは、「重複を探す」から「傘を立てる」への思想の転換と、決して削除しない、実行前に tar.gz のスナップショットを取る、1回分を丸ごとロールバックできる、という安全設計を扱う。ここではまず、3台のエンジンの中でのその位置づけを覚えてほしい。剪定を担当する1台である。

### 第3のエンジン「続」：Goals の Ralph Loop

最初の2台が変えるのは、Agent のセッションをまたぐ能力だ。第3のエンジンは違う。それが変えるのは、1回のセッションの中での Agent の粘り強さである。ソースコードは `hermes_cli/goals.py` にあり、コメントの中では「Hermes の Ralph loop」と呼ばれている。

仕組みは複雑ではない。goal とは、ユーザーが与え、複数ターンにわたって効き続ける目標である。ターンが終わるたびに、ごく小さな判定（judge）呼び出しが補助モデルに問う。この目標は、たった今の返答で満たされたか。満たされていなければ、Hermes は「続けて」という促しの文面を同じセッションに差し戻し、走り続ける。目標が完了するか、ターンの予算を使い切るか、ユーザーが止めるか、ユーザーが新しいメッセージを送るかするまでだ。

私が好ましく思う抑制の効いた設計がいくつかある。継続に使う促しは、通常の user message として1件追加されるだけで、system prompt には触れず、ツールセットも変えない。だからプロンプトキャッシュ（prefix cache）が無効にならず、コストが節約できる。判定役が万一壊れても、フェイルオープン（異常時継続動作）を選ぶ。壊れた判定役に進捗を止めさせてはならないからで、ターンの予算が最後の受け皿になっている。あなたはいつでも本物のメッセージを送って、継続の促しを横取りできる。

v0.18 では、このエンジンに「終了条件」が加わった。`/goal` を設定するときに「何をもって完了とするか」を明記でき、判定役は証拠に基づいて判定する。「だいたい終わったように見える」という感覚で判定するのではない。デフォルトのターンの予算は、依然として20ターンである。

> **ポイント**
>
> 最初の2台のエンジンが Agent に「使うほどあなたを理解する」力を与え、第3のエンジンが「一つの目標から手を離さない」力を与える。造る力、直す力、続ける力。この3つが揃って初めて、「Agent が自分で自分の手綱を作る」という全体像が完成する。

### 3台のエンジン、一枚の全景

3台の機械を並べて見れば、違いは一目瞭然だ。それぞれ異なる時間スケールで動き、それぞれ一つのことを担当し、互いの仕事を奪い合わない。

| エンジン | 動詞 | 発動のリズム | 何をするか | どこで動くか |
|---|---|---|---|---|
| Background Review | 造 | 会話10ターンごと／ツール実行10回ごと | 今回学ぶことを決める → メモリに書き、Skill を作る・直す | 本体の返答後にフォークされるバックグラウンドスレッド |
| Curator | 修 | デフォルト7日ごと＋アイドル2時間 | Skill ライブラリの剪定とアーカイブ（統合はデフォルトでオフ） | 独立してフォークされる Agent、補助モデルを使用 |
| Goals / Ralph Loop | 続 | ターンが終わるたびに1回判定 | 目標が未達成なら処理を継続し、複数ターンを走る | 同じセッション内、プロンプトを追加 |

これが、この閉じたループにおける最大の変化だ。初版に書かれていたのは「自己進化するはずの」Agent だった。v0.16.0 までに、それは発動条件を持ち、状態マシンを持ち、境界を持ち、ブレーキを持つ工学的なシステムになっていた。曖昧な約束から、ソースコードの中で1行ずつ指さして問いただせるインフラへと変わったのだ。

3台の中で、「造」と「続」は比較的理解しやすい。最も展開する価値があるのは「修」だ。その中には、この自己改善システムで最も抑制の効いた、最も直感に反する2つの設計が隠れている。次節では Curator の中に入り、自分で自分を整理する Agent のブレーキが、正確にはどこにかかっているのかを見ていく。

## §10 Curator：自己進化にブレーキをかける

自分で Skill を作る Agent は、遅かれ早かれゴミの山を作り出す。Hermes の答えは「そんなに作るな」ではない。自ら出勤してくる清掃担当を雇うことだった。そいつは決して物を捨てず、手を付ける前に必ずバックアップを取る。

### まず問題をはっきりさせる

前節で述べた通り、Hermes は会話のたびにバックグラウンドの振り返りをフォークし、今回学んだことを Skill として書き込む。聞こえは素晴らしいが、私の第一反応は心配だった。溜まる一方で、最後には似たり寄ったりの小さな Skill が何十個もできてしまうのではないか。

その心配は正しい。今日バグを直せば1件保存し、明日別のプロジェクトで似た落とし穴にぶつかれば、もう1件保存する。1週間もすれば、Skill のディレクトリには名前だけが違って内容は8割方重なったファイルが十数件、横たわっていることになる。Agent が Skill を選ぶたびに、その近重複の山をかき分けなければならず、トークンを無駄にするうえに、選び間違えやすくもなる。

これは仮定の話ではない。バックグラウンドの振り返りのプロンプトの中には、態度のはっきりした一文がある。「ほとんどのセッションでは、少なくとも1回は Skill の更新が生まれるべきだ。何もしないのは学習の機会を逃したのであって、中立的な結果ではない」。「できるだけ多く学べ」と命じられたシステムには、必ず「学びすぎる」という副作用が伴う。

Curator は、その副作用のために存在する。v0.12.0 で生まれ、その版は公式にそのまま「The Curator release」と名付けられた。副題は、底力の感じられる一文だった。"Hermes Agent now maintains itself"（Hermes Agent は今や、自分で自分を保守する）。それは自分自身の保守を始めたのだ。

§09 の比喩を引き継げば、Background Review が増殖を担い、Curator がアポトーシスを担う。ここで分解するのが、その「アポトーシスのエンジン」である。Karpathy も似たことを言っている。学習するシステムにとって、忘れることは学ぶことと同じくらい重要だ、と。

### どうやって起こされるか

Curator は、回りっぱなしの定時タスクではない。ソースコードの中に cron のバックグラウンドプロセスはなく、「アイドルによる発動」に頼っている。CLI の起動時や Gateway のティック（定期チェック）のついでに確認し、前回の実行から十分な時間が経ち、かつ Agent が十分に長くアイドル状態であれば、バックグラウンドプロセスをフォークして作業させる。

デフォルトでは、2つの関門を両方とも通過しなければならない。

```
前回の実行から7日以上 ＋ Agent のアイドル時間が2時間以上 → 保守処理を1回フォーク
```

私が好ましく思う細部がもう一つある。新規インストール後の最初のティックでは、すぐには作業しない。「前回の実行時刻」をそのまま「今」として記録し、自分に丸々7日の周期を待つよう強いる。コメントの言い方は実に率直だ。`hermes update` が終わった直後にあなたの Skill ライブラリを勝手にいじれば、体験はひどいものになる。あなたに丸1週間が与えられる。その間に、大事なものを pin（固定）し、不要なものを対象外にしておくことができる。

### 2段階方式：まず純粋な関数、次に LLM

Curator が実際に手を動かすときは、2段階に分かれる。第1段階では大規模モデルをまったく呼ばない。純粋な関数の状態マシンが、「その Skill がどれだけ長く使われていないか」に基づいて、そのライフサイクルを機械的に進める。

```
active（有効） ―14日使われない→ stale（陳腐化） ―30日使われない→ archived（アーカイブ済み）
```

この状態マシンの面白いところは、可逆で確定的なことだ。stale（陳腐化）とされた Skill も、もう一度使われれば自動的に active（有効）へ跳ね戻る。神秘的な要素はなく、大規模モデルの判断もなく、タイムスタンプによる計算だけだ。pin（固定）された Skill はこの工程を完全にスキップし、どれだけ時間が経っても動かされない。何らかの定時タスクから参照されている Skill もスキップする。一度も使われたことのない新しい Skill には猶予期間があり、少なくとも14日間存在しなければアーカイブされることはない。（6月に前版を書いた時点では、この2つの閾値はまだ30日と90日だった。今は引き締められている。）

なぜ第1段階では意図的に LLM を使わないのか。私の推測では、「ルールで決められること」と「判断が必要なこと」を切り分けるためだ。アーカイブするかどうかは純粋に時間の問題であり、モデルに判断させればコストの無駄になるうえに安定もしない。本当に判断基準が必要な仕事は、第2段階に残される。

第2段階になって初めて、補助モデルで動く Agent がフォークされ、Agent 自身が作った Skill を巡回して、1件ずつ判断する。残すか、直すか、別のものと統合するか、アーカイブするか。この段階には「考え方」がある。以下の考え方の一式は、v0.16 の時期における Curator の最大の進化である。

> **注意**
>
> v0.17 以降、この第2段階はデフォルトでオフになっている。Curator がデフォルトで実行するのは、コストのかからない第1段階の状態マシンだけだ。公式の理由はトークンの節約である。後述する「傘への統合」を行わせたい場合は、設定で `curator.consolidate: true` を自分で有効にするか、`hermes curator run --consolidate` を一時的に実行する必要がある。多くのチュートリアルが今も「デフォルトで統合される」前提で書いているので、この点には注意してほしい。

### 「重複を探して消す」から「傘を立てる」へ

初期の頃は、Curator がやっているのは重複の除去だと思いがちだった。似たものを2つ見つけて、1つを消す。しかし v0.16.0 の レビュープロンプトは、その理解を1行目で否定している。「これは傘式の統合であり、受動的な監査ではなく、重複探しでもない」。

違いはどこにあるか。重複除去の発想は「この2つは似ているか」であり、傘の発想は「人間の保守担当者なら、これらを独立した複数の Skill として書くか、それとも複数の小節を持つ1つの Skill として書くか」である。プロンプトの中では、「各 Skill のトリガーワードが異なること」を統合しない口実に使うことさえ明示的に禁止されている。トリガーワードの違いは理由にならない。1つの傘の下に収めるべきものは、収めなければならない。

具体的な手法は3種類ある。

| 手法 | どんなときに使うか | どうするか |
|---|---|---|
| 既存の傘に組み入れる | 傘になれる大きめの Skill が既にある | 兄弟 Skill の独自のポイントをパッチで取り込み、兄弟側をアーカイブする |
| 新しい傘を立てる | 既存の傘ではカバーできない | クラス単位の `SKILL.md` を新規に作り、散らかったものを収める |
| サブファイルに降格する | 内容は狭いが価値がある | 傘の下の `references`／`templates`／`scripts` に降格する |

この転換には、実にプロダクトらしい感覚がある。「良い知識ベースとはどういう姿か」という、定量化の難しい人間の判断基準を、自動保守のロジックの中にルールとして書き込んでいるのだ。プロンプトの中の一文が、私は特に気に入っている。「何百もの狭い Skill が、それぞれ1回のセッションの具体的なバグを1件ずつ扱っている。それはこのライブラリの特性ではなく、失敗である」。

### ブレーキの4つの設計

ここまで来ると、私と同じ本能的な不安を覚えるかもしれない。AI に自分の Skill ライブラリを自動で直させ、アーカイブさせる。万一、判断を間違えたらどうなる。万一、大事なものをアーカイブしてしまったらどうなる。

それこそが §10 の核である。Curator はアクセルを踏みっぱなしにする自動化ではない。そのブレーキは重く作られていて、1条ずつ取り上げる価値があるほど重い。

#### 第1のブレーキ：決して削除せず、アーカイブだけ

ソースファイルの冒頭には、不変条件が1条書かれている。"Never auto-deletes — only archives. Archive is recoverable."（自動では決して削除しない。アーカイブだけであり、アーカイブは復元できる。）アーカイブとは、Skill のディレクトリを `~/.hermes/skills/.archive/` の中へ移すことで、いつでも restore（復元）できる。Curator が自動で動くときに「削除」という動作は存在しない。せいぜい、隣の引き出しに物を移すだけだ。後に手動コマンドの `hermes curator purge` が追加され、一定の日数を過ぎたアーカイブを消去できるようになったが、それはあなた自身が押すボタンであり、Curator が勝手にやることではない。

#### 第2のブレーキ：統合の前にスナップショットを取る

Skill の統合や書き換えを行う前に、Curator は skills ディレクトリ全体を tar.gz のスナップショットにまとめ、`.archive/` ごと `.curator_backups/` の中に、UTC のタイムスタンプをファイル名にして保存する。注意してほしいのは、これが対象とするのは統合（consolidate）の工程だけだということだ。それは Skill の内容を変える唯一の操作である。v0.22 では統合がデフォルトでオフなので、剪定だけを行う回ではスナップショットは取られない。アーカイブそのものが取り消しの経路になっている（`hermes curator restore`）。

> **注意**
>
> 統合を有効にした後は、この回で広い範囲を間違って変更してしまっても、`hermes curator rollback` の1コマンドで回全体を取り消せる。今回アーカイブしたものも、以前にアーカイブしたものも、全部救い出せる。スナップショットには古いアーカイブも一緒に保存されるので、ロールバックは直前の一手だけの取り消しではなく、本当の意味での「時間を巻き戻す」操作になる。今は台帳も増えた。`hermes curator ledger` にすべての変更が記録され、`rollback 項目番号` でそのうちの1件だけを取り消すこともできる（なお `rollback --list` に表示されるのは、ライブラリ全体のスナップショットの方である）。

#### 第3のブレーキ：ドライランによる事前確認

自動実行が不安なら、`hermes curator run --dry-run` が、この回にやろうとしていることを全部列挙してくれる。ただし、あなたのライブラリには1文字も触れない。報告を審査し、問題がないと判断してから、本番の実行を行う。

これは、Martin Fowler の有名な枠組みに対応している。人と自動化システムの関係は、in the loop（すべてを自分で行う）か、on the loop（脇で監督し、介入できる）か、out of the loop（完全に任せきる）か。Hermes は明確に on the loop を選んだ。あなたが一歩ずつ見張る必要はないが、報告はいつでも審査でき、結果はいつでもロールバックできる。あなたを外に締め出したりはしない。

#### 第4のブレーキ：生成元情報で影響範囲を固定する

最も優雅なブレーキはこれだ。Curator は、どの Skill に触れてよく、どの Skill には決して触れてはならないと、どうやって知るのか。各 Skill の「生成元」の印（provenance、生成元情報）によってである。

| Skill の生成元 | 誰が作ったか | Curator は触れるか |
|---|---|---|
| 内蔵（bundled） | Hermes に出荷時から同梱 | デフォルトでは触れない（v0.16.0 以降、剪定を有効化する選択肢あり） |
| Hub からインストール | Hub から導入 | 常に免除。自動では決して触れない |
| ユーザーが前の Agent に依頼して作成 | あなたが明示的に Agent に書かせたもの | あなたのもの。Curator は決して手を出さない |
| Agent がバックグラウンドの振り返りで作成 | Agent 自身がフォークして作ったもの | ここだけが Curator の管轄範囲 |

実装は contextvar（文脈変数）という仕組みに頼っている。バックグラウンドの振り返りがフォークして動くとき、書き込みの生成元は `background_review` と印付けされる。その生成元から作られた Skill だけが `created_by: agent` と印付けされ、Curator の管轄に入る。あなたが手で書いたもの、導入したものは、永遠に安全だ。

この一文では立ち止まる価値がある。Agent の自己進化の影響範囲は、それ自身の領域の中に厳密に閉じ込められている。それが回収できるのは、自ら生え出てきたものだけだ。あなたの財産とその財産の間には、ソースコードの水準での所有権の境界線がある。

> **ポイント**
>
> 混同しやすい点がある。Skill を pin（固定）しても止まるのは、削除・アーカイブ・統合だけであり、内容の改善は止まらない。pin された Skill も、Curator によってより良い内容に直されることはある。pin が守るのは「消えないこと」であって、「変わらないこと」ではない。

### このブレーキは何に答えているか

「自己進化は制御を失わないか」という問いは、この種のシステムすべての頭上に懸かっている。多くの製品の答えは曖昧で、「安全機構があります」「継続的に監視します」といった程度のものだ。Hermes の答えは、ソースコードを指さして読み上げられる、具体的な設計の一式である。

> **推奨**
>
> 決して削除しない（アーカイブのみで復元可能）＋統合前の tar.gz スナップショット＋ドライランによる事前確認＋生成元情報による影響範囲の固定。どれもが「万一間違えたらどうするか」への回答になっている。
>
> **非推奨**
>
> 「充実した安全機構により、自己進化プロセスの制御可能性を保証します」。聞くと安心できるが、何か起きたときに何も受け止められない空文句である。

これこそが「ブレーキを取り付ける」ことの正しい姿勢だと私は思う。ブレーキは車の速さを制限するためのものではない。速く走る勇気を出させるためのものだ。決して削除せず、ロールバックでき、あなたのものには触れられないからこそ、あの「できるだけ多く学べ」という積極的な振り返りは、本当に積極的でいられる。このブレーキの一式がなければ、AI に自分のツールライブラリを自動で直させることなど、誰も怖くてできないはずだ。

次節では、この自己進化の中で最も直感に反する一筆を見ていく。「何を学ぶべきか」というルールの数々の外側に、Hermes は「何を学んではいけないか」のブラックリストまで書いている。自己進化する Agent にとって、本当の危険は学べないことではない。間違って学んだ後に、その間違ったルールで繰り返し自分自身を拒否し続けることだ。

## §11 いちばん大事な学びは「学ばないこと」

自己進化する Agent にとって、本当の危険は学べないことでは決してない。間違って学んだ後に、その間違ったルールを持って、何か月も繰り返し自分自身を拒否し続けることだ。Hermes の レビュープロンプトの中には、まさにこの事態を防ぐためのブラックリストが専用の一段として書かれている。

### 何か月も自分に跳ね返り続けるバグ

こんな場面を想像してほしい。ある日あなたが Hermes にウェブページの取得を頼んだところ、ちょうどその瞬間、環境の準備が整っていなかったためにブラウザツールがエラーを返した。Agent は試し、失敗した。

ここまではまだ正常だ。問題はその先にある。それには学習ループがあり（§09 を参照）、会話のたびにバックグラウンドの振り返りを行うサブ Agent をフォークして、自らに問う。今回は何を学んだか、Skill に書き込むべきか。

制約がなければ、それは一見もっともらしい結論にたどり着く可能性が高い。「ブラウザツールは使えない」。そして、それを自分のどこかの Skill ファイルの中へ、鄭重に書き込むのだ。

面倒はこの瞬間から始まる。環境はすぐに直り、ブラウザツールはまったく正常に動く。だが、そのルールは Skill の中に横たわったままだ。こうしてその後の何か月もの間、あなたがネットへ行くよう頼むたびに、それは自分が書いたその一文を引用して、あなたにこう言う。ブラウザツールは駄目です、できません、と。

Hermes のソースコードのコメントは、この現象を的確に描写している。1文をそのまま引用する（`agent/background_review.py` 出典）。

原文："Negative claims about tools or features ('browser tools do not work', 'X tool is broken'). These harden into refusals the agent cites against itself for months after the actual problem was fixed."（ツールや機能についての否定的な主張（「ブラウザツールは動かない」「X ツールは壊れている」）。これらは、実際の問題が直った後も何か月もの間、Agent が自分に反対するための引用として使い続ける拒否へと硬化する。）

「自分に反対するための引用として使い続ける拒否へと硬化する」。この言い回しは、相当に覚悟の定まったものだと思う。本来は使うほど賢くなるはずのシステムが、その学習能力のゆえに、自ら長期の落とし穴を掘ってしまうのだ。

### なぜ自己改善する Agent はこの落とし穴にはまりやすいのか

これは前段とつなげて読む必要がある。§09 で述べた通り、バックグラウンドの振り返りのプロンプトはかなり積極的な態度を取り、デフォルトでルールを多く書く側に寄っている。「何もしないのは中立的な結果ではなく、学習の機会を逃すことだ」。

つまり Hermes はデフォルトで学ぶ側であり、ルールを少なく書くよりも多く書く方へ傾いている。その傾き自体は正しい。それは Mitchell Hashimoto の有名な習慣に対応している。Agent が間違いをするたびに、`CLAUDE.md` にルールを1条追加するというものだ。だが、「間違うたびにルールを追加する」を自動化したとき、新しい問題が表面化した。

人間の間違いと環境の不具合は、ほとんど同じ姿をしている。どちらも「試した、失敗した」だ。しかし、この2つへの正しい対応は、天と地ほど違う。

> **学ぶべきもの**
>
> コマンドの引数を書き間違えた → 自分のミスだ。学んで、次は間違えないようにする。
>
> **学んではいけないもの**
>
> このマシンにたまたまそのバイナリが入っていなかった → 環境の一時的な状態であり、永久のルールとして学ぶべきではない。

「失敗から学ぶ」ことしかできない Agent は、この2つを見分けられない。それは2番目も1番目と同じに扱い、一時的な環境の故障を、永久の自己制限として律儀に学んでしまう。これこそが自改善の本当の2次リスクであり、それは学習能力そのものの中にあるのではない。今回の失敗が記憶に値するかどうかを判断する力の欠如の中にある。

### ブラックリスト：何を学んではいけないかを明示する

Hermes の対策は複雑ではないが、実に堅実だ。その レビュープロンプトの中に、「学んではいけないもの」のリストを専用に書いている（これも `background_review.py` 出典）。振り返りのサブ Agent は、Skill を書くかどうかを決める前に、まずこのブラックリストと照らし合わせなければならない。

| ブラックリストの分類 | 典型例 | なぜ学んではいけないか |
|---|---|---|
| 環境依存の失敗 | バイナリの欠落、`command not found`、認証情報の未設定 | このマシン、この時点の状態であって、タスクの普遍的な法則ではない |
| ツールへの否定的な断定 | 「ブラウザツールは使えない」「X ツールは壊れている」 | Agent が繰り返し引用し、長期にわたって自分を拒否する口実へと硬化する |
| 一度きりのタスクの残片 | 特定の PR 番号、特定のエラーメッセージの文字列、今日だけの仮称 | 今日のその1件にしか意味がなく、明日にはノイズになる |

このブラックリストの背後には、素朴な判断基準がある。人間の言葉に直せばこうだ。あるルールが今日のこの具体的な状況でしか成り立たないなら、それは永久のルールとして書かれるべきではない。

「本当の知識」と「一時的な状態」を見分けるのは、まさにこの基準による。コマンドの引数を書き間違えるのは普遍的な法則であり、学ぶに値する。どこかのマシンにあるパッケージが入っていないのは一時的な状態であり、学ぶに値しない。Agent は Skill を書く筆を執る前に、自らに問わなければならない。このルールは、環境が変わっても、機械が変わっても、まだ成り立つか。成り立たないものは、ブラックリストがその場で止める。

> **注意**
>
> この認識は、初版にはまったくなかった。4月時点の Hermes は、まだ「メモリを書き、Skill を作る」存在という理念の段階であり、自改善の本当の難しさは「どう学ばせるか」ではなく「どうやって乱雑に学ばせないか」にある、とは誰も気づいていなかった。ブラックリストは後から育ってきた最も成熟した一筆であり、v0.22.2 でもそのままソースコードに残っている。

### それでも学び間違えたら、生成元情報が影響範囲を固定する

ブラックリストは事前の予防だ。しかし、どれほど覚悟の定まったルールでも、すべての誤判断は防げない。漏れ落ちた悪い Skill が書き込まれてしまうことは、常にある。Hermes にはこの層の外側に、事後の受け皿がもう一つある。どの1件の誤った Skill であっても、それが起こし得る損害の範囲を、最初から固定してしまうのだ。

それが頼るのは、§10 で述べた生成元情報（provenance）の仕組みである。すべての Skill は「誰が作ったか」という印を持っている。出荷時に同梱されたもの、コミュニティから導入したもの、あなたが自ら書いたもの、Agent 自身がフォークして作ったもの。ここで覚えておくべきは、その所有権の境界線が「学んではいけないもの」という件において何を意味するかだけだ。Agent 自身が作った Skill だけが、Agent 自身によって回収され得る。

だから、ブラックリストに万一の漏れがあり、悪いルールがどこかの Agent 作の Skill に紛れ込んでも、それが汚染できるのは Agent 自身の領域だけだ。出荷時に同梱されたもの、Hub から導入したもの、あなたが自ら書いたものは、すべて安全である。ソースコードのコメントの言い方は直接的だ。ユーザーが前の Agent に書かせた Skill はユーザーのものであり、Curator は決して触れてはならない。

影響範囲について言えば、Agent が自習で書き損じた Skill は、最悪でも Agent 自身の領域だけを汚す。あなたが丁寧に保守している設定には届かず、安全スキャンを経た信頼できるコミュニティの Skill にも届かない。自改善のコストは、制御可能な小さな範囲の中に厳密に閉じ込められている。

この層の設計にこそ、本当の腕前が見えるのだと私は思う。§10 で述べた通り、Curator は決して削除せず、アーカイブだけを行い、統合の前には tar.gz のスナップショットを取って、1回分を丸ごとロールバックできる。生成元情報は、そのさらに手前に一枚を加える。自改善の影響が、Agent 自身の領域の外へ漏れ出すこと自体を許さないのだ。事前にはブラックリストが乱雑に学ぶことを止め、事後には生成元情報が影響範囲を囲い込む。前と後から、「自己進化」という、聞くと少し危うく感じられる事柄を、制御を失うことのない檻の中に閉じ込めている。

### この版で増えた「人の関与」の関門がもう2つ

6月から10月の間に、この考え方はさらに2歩前へ進んだ。どちらも、「何を学ぶか」に人が介入できる関門を加えるものだ。

1つ目は、メモリ書き込みの承認である。設定の `memory.write_approval` を有効にした後は、直前の会話の中でメモリを書こうとすると、まず確認が表示される。バックグラウンドの振り返りが書こうとするものは、先に一時保留され、あなたが `/memory pending` で見て、`/memory approve` か `/memory reject` で処理する。デフォルトはオフだ。§05 で、それが私の好みを自ら記録したのは、このスイッチがオフだった結果である。

2つ目は、Agent 自作 Skill の安全スキャン（`skills.guard_agent_created`）である。それ自身が書き出した Skill は、Hub から導入した Skill と同様に、スキャナを通らなければならない。dangerous（危険）と判定されたものは止められ、あなたに確認が求められる。

どちらの関門も、デフォルトでは比較的緩い。これはプロダクトとしての取捨選択だ。全部を有効にすれば、それが何かを学ぶたびにあなたの手を煩わせることになり、「自分で育つ」という体験は失われてしまう。私の推奨はこうだ。使い始めで、まだそれを信用しきれていない間は、メモリの承認を1、2週間有効にしてみる。それが何を覚えようとするのかを見て、感覚を掴んでから、オフに戻す。

### 自ら学ぶシステムが最も学ぶべきは、節度である

この節の題名に戻ろう。私たちは常に、Agent がもっと多くを学び、もっと勤勉に変わり、もっと速く進化することを期待している。しかし Hermes のこの仕組みが私に教えてくれたのは、直感に反することだった。自らを変更できるシステムにとって、「何を学んではいけないか」という境界は、「どれだけ学べるか」よりも、その下限を決める。

速く学ぶシステムほど、間違えたときの跳ね返りも深い。学習しない道具は、せいぜい今回1回失敗するだけだ。学習はするが節度のない道具は、今回の失敗をルールとして固定化し、その後のあらゆる機会で自分を失敗させ続ける。能力とリスクは、同じ硬貨の裏表である。

だから Hermes は「学ばせること」に多くの力を注ぎ、同じ真剣さで「乱雑に学ぶことを止める」ための関門をいくつも設けた。事前のブラックリスト、境界の生成元情報、回収の Curator、さらに選択式の人の承認。こうした覚悟の定まり方は、「使うほど賢くなる」という宣伝のどれよりも、私にそれを信頼させる。自分に向かって「これらは学んではいけない」と明示できる Agent こそが、本当の自己進化を語る資格を持つ。

次の Part では、さらに一層下へ潜り、このすべてを支える土台、三層メモリシステムを見ていく。学習ループがエンジンなら、メモリはその燃料であり、タンクだ。
