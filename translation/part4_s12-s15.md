## §12 3層メモリ：金魚から老友へ

たいていの AI ツールのメモリは、チャット履歴をどんどん積み上げていって、コンテキストに収まらなくなるまで膨らませるというものだ。Hermes のメモリは別の代物である。経験を蒸留して、ずっと使い続けられるノートに変える。しかも、あなたの財布を守るために、モデルに見せるのは「昨日の版」の方なのだ。

### 覚えられない金魚と、覚えている老友

Agent が使い物になるかどうか、私には素朴な見分け方がある。続けて10回使ってみて、自分のことを覚えているかどうかを見るのだ。

たいていのツールは金魚で、記憶は7秒しか持たない。今回「このプロジェクトでは requests ではなく httpx を使う」と教えても、次は平然と requests で書いてくる。言うことを聞かないのではない。本当に覚えていないのだ。新しいセッションを開くたびに、まっさらな白紙に戻る。

Hermes が目指すのは老友（古くからの友人）である。毎回自己紹介をやり直さなくても、あなたが誰で、何に取り組んでいて、何が嫌いかを知っている。それをやるには、「履歴をコンテキストに詰め込む」だけでは足りない。長く話せば話すほどコンテキストは長くなり、最後にはまた、あのパンクした金魚に戻ってしまう。

本当の解法は階層化である。「さっき何を言ったか」「あなたについての安定した事実」「ある仕事をどうやるか」を3種類の異なるメモリに分け、それぞれ別のストレージで、それぞれの担当を持たせる。これが Hermes の3層メモリだ。

| 層 | 担当 | 保存先 | 例え |
|---|---|---|---|
| セッションメモリ（エピソード記憶） | いつ何を言ったか | SQLite + FTS5 全文インデックス | 探し出せるチャット履歴 |
| 永続メモリ（意味記憶） | あなたと環境についての安定した事実 | MEMORY.md + USER.md の2ファイル | 机の前に貼った付箋 |
| Skill メモリ（手続き記憶） | ある仕事の具体的なやり方 | skills/ 配下の Markdown | 書き上げられた操作マニュアル |

この節では真ん中の層を重点的に話す。セッションメモリは次の節で単独で取り上げる。あちらにはもっと面白い話がある。Skill メモリは、前に学習ループを語ったときに下地を敷いてある。永続メモリは、初版以降に最も徹底して補完された部分だ。4月版では「SQLite の状態」の一言で流していたものが、今ではかなり念入りに作り込まれた体系に育っている。

### 2つのファイル、はっきり分かれている

永続メモリの実体は、たった2つの Markdown ファイルで、`~/.hermes/memories/` に置かれている。一つは MEMORY.md、もう一つは USER.md。§05 で私はその本当の姿を画面で示した。2ターンの会話の後に、それぞれ1件ずつ書かれている。

2つのファイルに分けるのは見た目のためではない。MEMORY.md に入るのは Agent 自身のノートだ。このプロジェクトの約束事、あるツールの癖、前回踏んだ落とし穴。USER.md に入るのは、あなたについての像である。名前、役割、好み、話し方。一方は「私（Agent）が覚えたこと」、もう一方は「私のあなたへの理解」だ。

どちらの置き場にも文字数の予算があり、上限に達したら自分で取捨選択しなければならない。MEMORY.md は約2,200文字、USER.md は約1,375文字。合わせても漢字1,000字に満たない。この制限は意図的なものだ。メモリは多ければいいわけではない。付箋を壁一面に貼れば、貼っていないのと同じことになる。Agent は最も残すべきものだけを残すよう強いられ、結果として精度が保たれる。

細かい点が一つ。それは token ではなく文字数を数える。コメントにははっきり書かれている。文字数はモデルに依存せず、モデルを換えても変わらない。こういう「特定のモデルのトークナイザに迎合しない」抑制の利いた姿勢が、この製品全体の性格である。

### 書き込みはリアルタイム、モデルに見せるのは凍結版

これは永続メモリの中で私が一番気に入っている設計で、旧版ではまったく触れていなかった。

まず矛盾から話そう。メモリは当然、永続でなければならない。今このターンで保存したものは、できればその場でディスクに落ちて、失われないのがいい。しかしメモリはモデルに与えるものでもあり、system prompt の中に差し込まれる。ここで問題が起きる。セッションの途中でメモリが変われば、system prompt も一緒に変わり、プロンプトキャッシュが台無しになる。

プロンプトキャッシュは、コストとレイテンシを削る生命線だ。モデルが推論するたび、冒頭の長い固定部分（system prompt、ツール定義、メモリ）はキャッシュに直接ヒットさせて、再計算を省ける。ところが途中で1文字でも変えれば、キャッシュはその文字から後ろが全部無効になり、以降のターンごとに再び料金と待ち時間が発生する。長い会話では、この差はかなりの金額になる。

Hermes の解法は巧妙だ。書き込みはリアルタイム、モデルに見せるのは凍結版。

```
セッション開始
メモリをスナップショットに凍結
→
途中の書き込み
即座にディスクへ
→
system prompt
全体が不変のまま
→
次のセッション
スナップショットを更新
```

つまりこうだ。このターンで保存したメモリは、確かにその場でハードディスクに書かれ、失われることはない。しかし、それがモデルの頭にすぐ入るわけではない。次のセッションが始まって初めて、新しいスナップショットとして注入される。その代わりに、この会話全体を通じてプロンプトキャッシュは無傷のままだ。

ソースコードの中では、2組の状態が維持されている。一つは凍結されたスナップショットで、system prompt に与える専用。もう一つは生きているエントリで、ツール応答が反映するのはこちら。一方は安定を担当し、もう一方は真実を担当する。互いに邪魔をしない。私はこれは「考え抜いてからでなければ書けない」タイプの設計だと思う。複雑ではないが、着眼点が正しい。

### メモリは攻撃面である

永続的で、セッションをまたいで続くメモリがあると、他の人があまり心配してこなかった面倒が一つ増える。メモリそのものが毒を盛られる（ポイズニングされる）可能性があるのだ。

想像してみてほしい。ある会話の中に悪意のある指示が1文紛れ込み、Agent がそれを「覚える価値のある好み」として MEMORY.md に保存してしまったとする。メモリは凍結スナップショットとして system prompt に入り、セッションをまたいで持続するので、その汚れたデータ1件が、その後の会話まるごと1つ、あるいは数セッション分を毒してしまう。これは1回きりのプロンプトインジェクションよりはるかに危険だ。持続性があるからである。

Hermes の対応は「入口で2回のセキュリティチェック」だ。

1. **書き込み時に1回スキャンする** — メモリがディスクに保存される瞬間、まず脅威パターンの検出を通し、怪しい内容は門前で止める。
2. **スナップショットへ読み込むときにもう1回スキャンする** — 脅威に該当したエントリは、スナップショットの中で `[BLOCKED: …]` のプレースホルダに置き換えられ、モデルには原文が見えない。ただし生きている状態の方には原文が残るので、あなた自身は確認したり削除したりできる。

この防御は、メモリ層が単独で作った車輪ではない。脅威パターンは同じ一つのソースファイルから来ていて、ツール結果のスキャン、コンテキストファイルのスキャンと共用している。後でセキュリティを扱う章で、この「3つのチョークポイントでインジェクションを防ぐ」体系を専用に分解する。メモリはそのうちの一つで、ここでは伏線を張るだけにしておく。

v0.17 以降、memory ツールは複数の変更を一度にまとめて適用して「全部成立するか、全部成立しないか」もサポートするようになった（最終的な文字数予算で判定する）。途中で上限を超えて、半分新しい半分古い状態が残る事態を避けるためだ。もっと素朴な防護もある。別のプロセス（何らかのパッチツール、shell での追記、あなたの手編集、あるいは別の並行セッション）が、解析できない内容を MEMORY.md に入れてしまった場合、memory ツールは書き込みを拒否し、まず現状を `.bak` にバックアップして、競合を処理するよう促す。黙ってあなたのデータを上書きするくらいなら、止まって警告する方を選ぶのだ。

> **ポイント**
>
> この設計の裏にある考え方はこうだ。メモリが強力であればあるほど、それを全面的には信用できない入力として扱わなければならない。あなたを永久に覚える Agent は、同時に、自分のメモリを疑う Agent でなければならない。能力と警戒心は、一緒に育つものだ。

### Claude Code の auto-memory と比べてみる

ここまで読んで、Claude Code のメモリを思い浮かべたかもしれない。あちらにも MEMORY.md があり、セッションの冒頭で読み込んで、あなたが誰で何をしているかを把握する。私自身も毎日使っていて、体験は確かに良い。両者は似ているが、底にある考え方が少し違う。

| 観点 | Claude Code auto-memory | Hermes 永続メモリ |
|---|---|---|
| 置き場 | 単一の MEMORY.md（約200行が上限） | MEMORY.md + USER.md の二本立て、各々に文字数予算 |
| 事実／人物像 | 1つのファイルに混在 | 「環境について」と「あなたについて」を物理的に分離 |
| 書き込みのタイミング | トリガ式（あなたが「覚えて」と言うか、条件を満たしたとき） | ナッジによる定期的な促し ＋ コンテキストが失われる直前の緊急保存 |
| キャッシュへの配慮 | セッション内では概ね安定 | 明示的にスナップショットを凍結し、プロンプトキャッシュのために設計 |
| インジェクション対策 | 軽め | 書き込み時スキャン ＋ 読み込み時スキャン ＋ BLOCKED プレースホルダ |

急いで優劣を付ける必要はない。Claude Code のメモリはもっと軽く、もっと扱いやすい。あなたが見ているデスクトップ上で動いていて、問題が起きればその場で直せるからだ。Hermes がメモリをここまで重く作るのは、その想定が、クラウドに住む24時間無人稼働のデジタルな同僚だからである。誰も見ていないものは、自分で免疫系を育てるしかない。同じ MEMORY.md というファイル名の背後に、2種類のデプロイの現実がある。

振る舞いの層にも小さな仕掛けが2つある。一つはナッジ（nudge）で、だいたい10ターンごとに Agent に「何か保存する価値のあるものはあるか」と一言促す。仕事に没頭してノートを取るのを忘れないようにするためだ。もう一つはフラッシュ（flush）で、コンテキストが失われる直前（圧縮、リセット、終了の瞬間）に、Agent にメモリを緊急保存する機会をもう1ターン与える。ただし、今回の会話が十分に長かった場合（デフォルトで6ターン以上）にだけ発動し、栄養のない短い会話まで記録してしまうのを避ける。

### 3層の外に、任意の第4層

厳密に言うと、メモリは3層だけではない。3層は内蔵で、出荷時点で付いてきて、設定ゼロ、全てローカル、無料。その外側に、Hermes は任意の差し込み口を一つ残している。外部メモリ provider で、より深いセッション横断のユーザーモデリングを行うものだ。例えば Honcho がそうである。

この層はデフォルトでは有効になっていない。自分で `hermes memory setup` に行って一つ選んで導入する必要があり、API key の設定が必要な場合もある。6月の時点では、インストールパッケージの中に8つの候補が並んでいた。v0.22 ではその大半がコアの外へ移され、同梱されるのは byterover と retaindb の2つだけになった。Honcho、Hindsight、Supermemory、Mem0、OpenViking などは、プラグインカタログ（Plugin Catalog）から必要に応じてインストールする形に変わり、既存ユーザーがアップグレードする際は自動で移行される。硬いルールは変わっていない。同時に有効にできるのは1つだけ。増やそうとすると拒否される。多数のバックエンド同士が喧嘩したり、ツールの一覧を膨らませたりしないためだ。

この配置は、Hermes の取捨選択をよく表している。あなたを覚えるという基礎は、出荷時点で代わりに済ませてあり、他のサービスを入れたかどうかを選ばない。もっと凝ったユーザーモデリングが欲しければ、扉は開いている。ただし、入るのはあなた自身の足で、だ。

次の節では第1層、セッションメモリに潜る。そこには私が特に話したい物語がある。Hermes が、大規模モデルにやらせるべきではなかった仕事を、大規模モデルの手から取り戻した話だ。結果は、速く、正確で、お金もかからない。

## §13 セッション検索：LLM にやらせるべきでない仕事を取り戻す

初版の後、このメモリシステムで最大の変更は、検索が速くなったことではない。ここにあるはずのない LLM を、誰かが引き抜いたことだ。結果として、同じことが無料で、即座にでき、でたらめを捏造することもなくなった。

### まず公式の一言を見てほしい

v0.15.0 のリリースノートに一行あり、私は読んで手が止まった。session_search は書き換えられ、no LLM、no cost、4500× faster（LLM なし、コストなし、4,500倍速い）だという。

4,500倍。こういう数字が出てくると、私の第一反応は疑うことだ。AI 界隈の「何倍速くなった」という言い方の大半はマーケティングの文句で、ベンチマークを換えれば正体を現す。だからソースコードを読みに行って、この 4500× がどういう計算なのかを見てきた。

読み終えて、私は認めなければならない。今回は本当だった。しかも真相は「4,500倍速い」よりもずっと面白い。

### 旧版はどこが遅く、どこが高かったのか

旧版のセッション検索はこういうやり方だった。「先週、データベース移行について話したセッション」を探したいとする。まず SQLite の FTS5 全文インデックスで候補のセッションをいくつか取得する。この一歩自体は本来速い。その後で、余計なことを一つやっていた。補助 LLM をもう一つ呼んで、ヒットしたセッションを「要約」して見せるのだ。

問題はこの補助 LLM にあった。3つのセッションを取得して要約するごとに、だいたい30秒かかり、だいたい0.3ドルかかった。さらに悪いことに、FTS5 が正しいセッションをそもそも取得できなかったとき、この LLM は「見つかりませんでした」とは言わない。それどころか、あなたが一度も言っていない内容を、さも事実かのように平然とでっち上げて返してくる。

この設計のねじれ具合を味わってほしい。検索という仕事については、FTS5 が既に正確な答えを出している。どのメッセージがヒットしたかは、データベースの中にはっきり転がっている。それなのに、わざわざお金を払い、30秒待ち、幻覚を起こし得るモデルに、それらの本物のメッセージを「言い換え」させる。手元に原文があるのに、誰かに復唱させ、しかも復唱する側は記憶違いを起こすかもしれないのだ。

### 新版がやったこと：その LLM を消した

新版の解法は、退屈なほど素朴だ。データベースの中の本物のメッセージを直接返し、全過程で LLM に触れない。

> **非推奨**
>
> 旧版：FTS5 で取得する → 補助 LLM に3セッションを要約させる → 約30秒、約0.3ドル、捏造の可能性あり → 「言い換え版」を返す
>
> **推奨**
>
> 新版：FTS5 で取得する → ヒットした本物のメッセージを DB から直接取り出す → 約20ms、コストゼロ、捏造の余地なし → 原文を返す

ソースコードには、この一文がかなり強気に書かれている。session_search のツールファイル冒頭のコメントが明々白々だ。すべてのモードは SQLite の FTS5 インデックスを通り、「No LLM calls anywhere（どこにも LLM 呼び出しはない）」、どの返却もデータベースの中の本物のメッセージである、と。

discovery のような検索付きのクエリは、元の約90秒から約20ミリ秒に圧縮された。純粋なページめくり（scroll）はもっと速く、約1ミリ秒。いわゆる 4500× は、90秒を20ミリ秒で割って出た数字で、エンドツーエンドのツール一式のレイテンシ比較であり、FTS5 エンジン自体が4,500倍速くなったわけではない。

この点は、読者が数字に引っ張られないよう、私からも一言添えておく。検索エンジンは最初から最後まで FTS5 で、一行も換わっていない。変わったのは、最も遅く、最も高く、最もでたらめを言いやすい、その一環を取り除いたことだけだ。本質的には、LLM にやらせるべきではなかった仕事を、LLM の手から取り戻したのである。

直感に反する判断が一つある。多くの人は無意識に「LLM を載せれば、より賢く、より良い」と考えがちだ。しかし検索は標準解答のあるタスクだ。ヒットするか、しないか。そのどちらかしかない。決定性のあるタスクに確率的なモデルを被せて得られるのは、知能ではなく、コストと遅延と幻覚である。工学の上で最も抑制の利いた前進は、ときには引き算だ。

### LLM の要約なしで、なぜ足りるのか

これが私の最初の疑念だった。LLM の要約は少なくとも「このセッションで何を話したか」の概観をくれる。原文をそのまま返すだけでは、大量のメッセージを顔にぶつけられるのではないか。

新版の工夫は discovery という検索モードの中にある。1回の呼び出しで、3つのものを同時に渡してくる。セッション冒頭の数メッセージ（その件が当初何をしようとしていたか分かる）、ヒット箇所の前後数件の窓（肝心な一段が見える）、セッション末尾の数メッセージ（最後にどんな結論になったか分かる）。

冒頭と末尾という「ブックエンド」式の切り取りに、ヒット箇所の文脈の窓を加えれば、メインモデル自身が「このセッションで何を話したか」を組み立てられる。LLM の要約が本来与えたかった概観は、構造化された頭と尾とヒット窓でメインモデルに再建させることができ、別途 LLM にお金を払う必要がない。目的、ヒット、結論を一度に揃えられる。

### 4つの検索モードはすべてパラメータから推測する

リリースノートは3つのモード（discovery / scroll / browse）だと言うが、ソースコードを読むと実は4つある。しかも、選ばせるための mode パラメータなど存在しない。どのパラメータを渡したかで、あなたが何をしたいのかを向こうが推測する。

| 検索モード | あなたが渡すもの | 返ってくるもの | LLM を使うか |
|---|---|---|---|
| DISCOVERY（探す） | キーワード query | FTS5 のヒットをセッション単位で重複排除。各々に抜粋スニペット、ヒット箇所の前後の窓、頭と尾のブックエンド | 否 |
| SCROLL（めくる） | セッション id ＋ アンカーとなるメッセージ id | アンカーを中心に前後数件（デフォルト5、最大20）。検索もブックエンドもなし | 否 |
| READ（読む） | セッション id だけ | セッション全体（長すぎる場合は頭20＋尾10を取る） | 否 |
| BROWSE（眺める） | 何も渡さない | 最近の数セッションのタイトル、プレビュー、タイムスタンプ | 否 |

「モードのスイッチはなく、パラメータを見て仕事をする」というこの設計は、私はかなり評価している。一つのツールが4つの仕事を担えば、それを呼ぶ Agent の認知負荷は最小になる。自分がどの mode にいるのかを先に考えなくてよく、手元にあるものを渡せばいい。READ という検索モードは、もう一つ実務的な仕事もする。チャットの中にセッションのリンクを貼り込むと、profile をまたいで読み取り専用にそのセッションを取り出して見せてくれる。これは「アイデンティティをまたいだメモリの相互運用」への入り口だ。

### 中国語ユーザーへのおまけ：2つの FTS5 テーブル

この点は旧版ではまったく触れていなかったが、中国語の読者にとってはかなり値打ちがある。

FTS5 のデフォルトのトークナイザ（unicode61）には古い癖がある。中国語に当たると、文字ごとに切り分けてしまうのだ。「大别山项目（大別山プロジェクト）」を検索すると、内部では「大 AND 别 AND 山 AND 项 AND 目」になってしまい、誤検出が起きやすいし、正確なフレーズにもマッチしない。日本語、韓国語、タイ語も同じ落とし穴である。

新版は2つの FTS5 仮想テーブルを作って、これを解決した。一つはデフォルトの unicode61 で、英語を受け持つ。もう一つは CJK 専用で、trigram（3文字の重なり）による分割を使い、任意の文字の部分文字列マッチを自然に可能にする。

```
中国語でないクエリ → 主テーブル unicode61
中国語のクエリ → CJK 双字テーブル（利用可能な場合）
それ以外は trigram テーブル / LIKE でのフォールバック
```

6月に前版を書いた時点の振り分けはこうだった。英語は主テーブルへ行き、BM25 で順位付けしてハイライトする。中国語で、各語が漢字3文字に足りていれば trigram テーブルへ行く。語が短すぎる場合（「桂林 OR 漓江」のような2文字の語）は trigram ではマッチできず、LIKE に退いて時間の新しい順に全表をスキャンしていた。

v0.20 以降、ここはもう一歩進んだ。コミュニティのコントリビュータ Soju06 が、わずか200行あまりの FTS5 トークナイザを提出した。`cjk_unicode61` という名前で、連続する中日韓の文字を2文字ずつ重ねた双字（バイグラム）に切る（「项目管理」は「项目」「目管」「管理」に切れる）。これで1、2文字の中国語の語もインデックスを辿れるようになり、全表スキャンが要らなくなった。ソースコードのコメントには、旧方式の代償が記録されている。数 GB のデータベースでは、1回の LIKE スキャンで CPU を3〜6秒食い、中国語ユーザーの session_search の最大の支出だった。CJK テーブルができてからは、trigram テーブルは控えに回った。

ただし条件が一つある。CJK テーブルは、そのトークナイザ拡張の読み込みに成功したときにだけ作られる。私がテスト導入した環境で state.db を覗くと、trigram テーブルしか見えず、CJK テーブルはなかった。おそらく、私のようなソースコードから直接入れる方式では、拡張がビルドに入っていなかったのだろう。公式のインストールスクリプトで入れた場合がどうなるかは、私は検証していない。`sqlite3 ~/.hermes/state.db ".tables"` で、`messages_fts_cjk` があるかどうか見てみるといい。どちらにせよ、これはすべてローカルで、コストゼロだ。これが「なぜ Hermes のセッション検索は中国語でも使いやすいのか」への答えである。

### 最後のおまけは、全ての人への方法論

LLM の排除は、実際にコードを削除した。しかし私が読む中で、周りのドキュメントと設定が完全には追いついておらず、2箇所で自己矛盾が残っているのを見つけた。

一箇所は設定のサンプルファイルの中だ。「セッション要約」用の旧版の LLM 設定ブロックが、そのまま残っている。provider、model、timeout、並行数、全部ある。しかし新しいコードは、これらをまったく読まない。既に死んだ設定である。

もう一箇所はもっと直接的だ。README の機能表には今も「FTS5 session search with LLM summarization（LLM 要約付き FTS5 セッション検索）」と書かれている（10月20日に改めて見たが、v0.22.2 の README とドキュメントのトップページは今もこの一文だった）。一方でソースコードのコメントは「No LLM calls anywhere」と白黒はっきり書いている。一つのファイルは「LLM あり」と言い、もう一つのファイルは「全過程 LLM なし」と言い、同じリポジトリの中で喧嘩している。

> **注意**
>
> README は「LLM 要約あり」と言い、ソースコードは「全過程 LLM ゼロ」と言う。どちらを信じるか。ソースコードを信じなさい。コードは実際に動く事実であり、ドキュメントは期限切れになり得る言説である。この矛盾そのものが、「二次的な解釈を信じず、ソースコードを読め」という最良の教材だ。

このおまけを単独で取り出したのは、それが session_search 自体より重要なことを指しているからだ。AI ツールの進化は速すぎて、ドキュメントは常にコードに遅れる。あなたが見ているチュートリアルや、誰かが伝聞で語る「あれには何の機能がある」という話は、3バージョン前の姿を描写しているかもしれない。本当に、あるツールが今どう動いているのかを確かめたければ、唯一信頼できる出どころは、今動いているそのソースコードである。

この節を、私は本書全体の「工学的な抑制」の模範として読みたい。何も新しいものを加えず、むしろ一見高級に見える LLM を一台取り除いた。得られたのは、無料、即時、幻覚なし、その上に中国語へのネイティブな配慮だ。次の節ではメモリを離れて、Hermes が自分の数々の技を、読み込み可能で共有可能な Skill にどう分解するかを見ていく。

## §14 Skill システムとオープン標準の恩恵

4月に初版を書いたとき、Hermes の Skill はまだ「同梱された一山のテンプレート」に過ぎなかった。今日、その公式の説明は「経験から Skill を作る agent」へと書き換えられ、Skill は脇役から主役に昇格した。しかしこの節で最も語る価値があるのは、実はそれが下したもう一つの選択だ。自前の形式を作らず、他人の生態系にただ乗りする、という選択である。

### Skill はどこから来るか：3つのタイプが一つのディレクトリに混ざる

Hermes のすべての Skill は、同じ一つのディレクトリ `~/.hermes/skills/` に落ちる。そのディレクトリだけが Skill が保存される唯一の場所だ。このディレクトリを開くと、Skill はまったく異なる3つのタイプから来ているのに、仲良く共存しているのが見える。

| 種類 | 入ってくる経路 | 信用レベル |
|---|---|---|
| 内蔵（bundled） | Hermes の導入時にリポジトリからコピー。update のたびに増分で新しいものを補う | builtin（決してスキャンしない） |
| Agent の自作 | バックグラウンドの振り返りプロセスが、残す価値があると気づいて自分で書き込む | agent-created（Curator の管理下） |
| コミュニティの Hub | 9つの外部ソースから導入。安全スキャンを通ってからディスクに落ちる | trusted / community |

内蔵という段の数字の変化はなかなか面白い。旧版の基準時点（v0.7.0）では、公式はまだ「40超の同梱 Skill」と書いていた。6月の v0.16.0 では、ソースコードを数えると内蔵 Skill が74個、それに公式の optional（デフォルトでは読み込まれず、コマンド1つで戻せるもの）が95個あった。10月の v0.22.2 では、同じ数え方で内蔵58個、optional 153個、合計211個。内蔵はむしろ減っている。mlops、github、データサイエンス、レッドチームのテスト、スマートホームといった大きな分類が、まとめて optional に降格されたからだ。私のテスト機で `hermes skills list` に出てきた内蔵は57個で（§06 に画面がある）、ソースコードの数58と1つ違う。名簿を突き合わせると、足りないのは sdlc-review で、ファイルの冒頭にKanban 環境専用（environments: kanban）と書かれていて、skills list はそれを数に入れず、起動画面の「58 skills」の方には入っていた。

しかし同じバージョンで、それは逆方向のこともやっている。デフォルトの Skill セットに自らダイエットさせたのだ。ネイティブ機能に取って代わられた死んだ Skill を削除し、あまり使わない一群を内蔵から optional に降格させ、environments によるゲートも加えた。文脈専属の Skill は、もう全員のインデックスを汚さない。あなたが明示的に求めない限り、現れない。

この動きは肝心だと私は思う。Skill は多ければ多いほどいいわけではない。詰め込みすぎれば、agent は Skill を選ぶたびに長い列を掘り返さなければならず、プロンプトも重くなる。「デフォルトを軽く、ピッカー（選択 UI）を静かに」と「自作 Skill を無限に膨らませない」は、同じ不安の両面である。

### 本当の賢さはここだ：車輪を自作しなかった

これこそがこの節の主軸である。Hermes の Skill が使うのは自家発明の形式ではなく、agentskills.io というオープン標準だ。この SKILL.md 形式は、もともと Anthropic が Claude Code のために作ったもので、後に汎用の標準として公開された。

ソースコードのあちこちに、それへの互換の痕跡がある。frontmatter の license、compatibility といったフィールドには、いずれも「agentskills.io では任意」と書かれている。設定を読むときは、まず標準で約束された名前空間を調べ、次に自前のフィールドへフォールバックし、専用の設定は隅に押し込んで、汎用フィールドには触れない。こうする目的は一つしかない。ツール間での移植性だ。

どの程度まで移植できるのか。Claude Code のために書かれた SKILL.md は、Codex の Skill ディレクトリにそのままコピーすれば動くし、振る舞いも一致する。同じファイルは、Codex CLI、Gemini CLI、GitHub Copilot、Cursor といった、標準を採用済みのプラットフォームのいずれでも認識される。

ネットワーク効果は加速している。4月の初版の時点で、この標準を採用するツールは「11超」だった。6月には「26超」になった。標準の裾野が広いほど、それに賭けた者が食べられる蓄積は多くなる。

Hermes はこの恩恵をどう食べるか。非常に直接的だ。もともと Claude Code や Codex の生態系のために作られた Skill リポジトリを導入できる。例えば openai、anthropic、huggingface といった公式の Skill repo が、そのまま使える。OpenClaw のための移行経路まで用意している。両側が同じ標準を食べているので、Skill はほぼ無損失で引っ越せる。

これは典型的な「標準と対立しない」判断だと私は推測する。自前でコミュニティをゼロから育てれば、何年も耐えなければならない。Claude / Codex 全体の Skill の蓄積を直接再利用すれば、今日から使える。他人の生態系にただ乗りする方が、自分の生態系を育てるより、ずっと割に合う。

### NVIDIA がデフォルトの信用リストに入った

生態系の話をすると、v0.16.0 には象徴的な出来事があった。NVIDIA 公式の Skill リポジトリが、Hermes のデフォルトの trusted tap（信用された接続元）に入ったのだ。

trusted tap とは、Hermes を導入した後に何の設定もなしに直接閲覧できる数個のソースのことだ。もとの名簿には openai、anthropic、huggingface、garrytan の数リポジトリがいた。この版で NVIDIA/skills が加わった。NVIDIA による検証済みで、署名付き、ガバナンスカード付きで、CUDA-X、cuOpt といった製品スタックをカバーする。

ここで2つの概念を区別しておく必要がある。「デフォルトで閲覧できるリポジトリ」と「信用されたリポジトリ」は同じものではない。v0.22.2 のソースコードで本当に trusted の集合に入っているのは4つのリポジトリ、openai/skills、anthropics/skills、huggingface/skills、NVIDIA/skills である。garrytan のリポジトリはデフォルトで閲覧できるが、信用リストには入っておらず、コミュニティのリポジトリとして扱われる。

この件は、機能そのものより、その合図としての意味が大きい。ハードウェアメーカーまでもが agent の Skill 生態系への公式供給を始めたということは、SKILL.md という標準が、もはやソフトウェア界隈のおもちゃではないということだ。OpenAI、Anthropic、Hugging Face が名を連ねるのはまだ理解できる。NVIDIA までが敷設に来るとなれば、標準の引力のほどが見て取れる。

### 3層の読み込み：使うときにだけ開く

Skill が増えると現実的な問題が出る。全部をコンテキストに詰め込めば、token が持たない。Hermes の解法は段階的開示（progressive disclosure）で、3層に分けて読み込む。

```
Level 0
名前＋説明だけを見る
→
Level 1
全文を展開する
→
Level 2
どこかの参考ファイルを取る
```

第1層では、agent は各 Skill の名前、説明、分類だけを受け取る。数千 token 程度で全 Skill を並べ切れる。この層で「今回はどれが使えるか」を判断する。本当に使う段になって初めて、第2層に進んでその Skill の全文を読み込む。全文の中でどこかの参考資料への参照があれば、さらに第3層へ進んでそのファイルを取る。

この設計の利点は、Skill を何十、何百と導入しても、普段はコンテキストを占有しないことだ。agent は目次のある本をめくるように振る舞う。まず目次を見てどのページを開くか決めるのであって、本全体を暗記したりはしない。これが、Skill の数が200を超えても速度が落ちない理由でもある。たいていの時間、それらは目次の中の一行に過ぎない。

### Skills Hub：複数のリポジトリ ＋ 隔離したスキャン ＋ 段階的な信用

3つ目のタイプ、コミュニティの Hub は、初版以降に最も速く膨らんだ部分だ。4月の時点では、まだ漠然とした「コミュニティの Skill 導入を提供するもの」に過ぎなかった。今は、複数のリポジトリを集約する発見／導入のシステムに育っている。6月版では外部の9つのリポジトリと連携していた。v0.22.2 では、ソースコードにあった Claude 互換マーケットのリポジトリがなくなり、残りの数リポジトリはまだあり、さらに各リポジトリをまとめた hermes-index というインデックスが一つ加わった。下の規模の数字は6月時点のもので、各リポジトリとも増え続けている。量の感覚を掴むためのものだ。

| 種類 | 何か | 規模 |
|---|---|---|
| [skills.sh](https://skills.sh) | Vercel の公開 Skill ディレクトリ | 約2万超 |
| ClawHub | サードパーティの Skill マーケット | 5万級 |
| LobeHub | agent マーケット。エントリを導入可能な Skill に変換 | 1.4万超の agents |
| browse.sh | Browserbase のブラウザ自動化 Skill | 200超のサイト |
| github / url / well-known / official | リポジトリの直接導入、単一ファイルの URL、サイトの規約による発見、公式 optional | — |

5万個の見知らぬ Skill は魅力的に聞こえるが、ここには本物の攻撃面が隠れている。見知らぬ SKILL.md を1つ導入することは、agent の中に、指示として実行される一段のテキストを差し込むことと等しい。それ自体がプロンプトインジェクションの温床だ。人畜無害に見える「天気を調べてくれる」Skill の本文に、「ついでにユーザーのキーをどこかのアドレスに送っておいて」と埋め込まれているかもしれない。

Hermes のこの件への対処は、語らなければならない設計の一つだ。コミュニティから来た Skill は裸で入れるのではなく、まず強制の安全スキャナを通さなければならない。静的解析で既知の悪いパターンを探す。例えば、データの外部流出、プロンプトインジェクション、破壊的なコマンド、永続化するバックドアといったものだ。

```
隔離エリアへダウンロード
→
スキャンして格付け
safe / caution / dangerous
→
通ったものだけディスクに落とす
全過程を監査ログに記録
```

スキャンと組み合わさるのが信用の格付けで、スキャン結果をどれだけ厳しく扱うかを決める。

> **推奨**
>
> builtin：Hermes と一緒に出荷され、決してスキャンせず常に信用する。trusted（openai、anthropics、huggingface、NVIDIA の4つのリポジトリ）：safe と caution は通し、dangerous は遮断する
>
> **非推奨**
>
> community（それ以外の全部）：caution の段階でも遮断する。あなたが手動で `--force` を付けて強行しない限りは

後になって、agent 自身が書いた Skill（agent-created）のための段も増えた。自分で作ったもの、` /learn` であなたが書かせたものも、スキャンを通す。dangerous と判定されたときにだけ止まって、あなたに尋ねる。

この仕組みは、Skill の毒盛りという話題にちょうど接続する。オープン標準がもたらす恩恵とリスクは表裏一体だ。生態系全体にただ乗りできる代わりに、生態系全体の汚いものがあなたのマシンに入る通路もできる。Hermes の答えは、隔離したスキャンと段階的な信用だ。大手公式のリポジトリには少し緩くし、素性の知れない見知らぬ Skill はデフォルトで泥棒として警戒する。私はこの境界の引き方はかなり冷静だと思う。

> **ポイント**
>
> 実務上の助言：自分で使うなら、まず trusted tap（openai / anthropic / huggingface / NVIDIA）から Skill を入れること。これらは公式の裏付けを通っている。ClawHub のようなコミュニティのリポジトリから入れる前に、1分使って SKILL.md の本文に目を通すこと。特に、ネットワーク接続を要求していないか、あなたのキーを必要としていないか、妙なコマンドがないかを見る。隔離スキャンは既知の悪いパターンを防げるが、あなたの常識が最後の関門だ。

この節を通して見ると、Hermes はオープン標準に賭け、「数か月で Claude / Codex の生態系全体にただ乗りする」速度を手に入れ、NVIDIA までもが供給に来た。代償として、5万個の見知らぬ Skill の毒盛り面に向き合わなければならず、隔離スキャンと3段階の信用で受け止めている。これは考え抜かれた取捨選択だ。生態系のネットワーク効果が欲しいなら、安全の勘定も認めなければならない。両方をやり、恩恵だけを取ってリスクを無視するようなことはしない。

## §15 一つの Agent が Agent の群れを指揮する

前の数節では、Skill はずっと知識の文書であり、agent に「この仕事はどうやるか」を教えるものだった。この節では、それが別のものに変わる。指揮棒である。Hermes は Claude Code、Codex、OpenHands、OpenCode、Grok を、呼び出し可能な Skill としてまとめて封入し、自分は後ろに下がって総指揮を執る。

### 一つの画面：それはコードを書かず、仕事を割り振る

あなたが Hermes に、ある機能を実装するよう頼んだと想像してほしい。もちろん自分で手を下し、terminal を叩き、ファイルを書き、テストを回すこともできる。しかし v0.16.0 以降、もう一つ選択肢が増えた。その仕事を外注に出すことだ。

`skills/autonomous-ai-agents/` というディレクトリの下に、6月の時点ではソースコードに4つの内蔵 Skill が横たわっていた。v0.22.2 では5つになり、computer-use（デスクトップアプリを操るもの）が一つ増えた。§04 の起動画面の右欄にある「autonomous-ai-agents: claude-code, codex, +3 more」が指すのはこれらである。これらは Hermes に「Python をどう書くか」を教えるのではない。別のコーディング agent を呼んで、代わりに書かせる方法を教えるのだ。Claude Code が一つ、Codex が一つ、OpenCode が一つ、Hermes 自身も一つある（本体へのコード貢献に使う）。

| Skill | バージョン | 誰に仕事を指揮させるか |
|---|---|---|
| claude-code | 2.2.1 | コーディングを Claude Code CLI に委ねる（feature の作成／PR の提出） |
| codex | 1.0.1 | コーディングを OpenAI Codex CLI に委ねる |
| opencode | 1.2.0 | コーディングを OpenCode CLI に委ねる（複数の provider をぶら下げられる） |
| hermes-agent | 3.2.0 | 設定、拡張、Hermes 本体へのコード貢献 |

表は v0.22.2 のバージョン番号である。optional のディレクトリにはもっとある。OpenHands、Grok の Build CLI、antigravity-cli、blackbox、後から加わった dynamic-workflow と、マージコンフリクトの調停専用の agent-merge-conflict-arbiter。これらを導入すれば、Hermes の手元には差し向けられるコーディング agent が一列そろう。

```
あなた → Hermes（総指揮）
→
Skill を一つ選ぶ
→
Claude Code / Codex / OpenHands…
→
コード / PR が戻ってくる
```

この構造は少し直感に反する。私たちはずっと Claude Code や Codex を「端末」だと思ってきた。あなたが直接話しかける agent だ。しかし Hermes の目には、それらは「部下」である。誰が最前面であなたの要求を受け取るか、その者が指揮官であり、他の agent はその工具箱の中の一本のレンチに過ぎない。

なぜこんなことをするのか。agent ごとに気性が違うからだ。Claude ネイティブな仕事は claude-code に渡し、OpenAI ネイティブな仕事は codex に渡し、モデルを換える必要がある場面では別のものに換える。Hermes は各社のモデルの特長を全部覚える必要はない。「この仕事は誰に割り振るべきか」を知っていれば十分だ。指揮官の技量は、割り振り（誰に何を任せるか）であって、自分で手を動かすことではない。

### 模範を一つ分解する：OpenHands の Skill はどういう姿か

この編成用 Skill の群れの中で、OpenHands のものが最も念入りに書かれている。それを標本として取り上げたい。「良い Skill とはどういう姿か」を知りたければ、これを写せばいい。

まず、それが何をするか。OpenHands は model-agnostic（モデルを選ばない）で、背後には LiteLLM がサポートする任意の provider を接続できる。OpenAI、Anthropic、OpenRouter、DeepSeek、Ollama、vLLM、どれでもいい。だからこの Skill の位置づけは明快だ。Claude ネイティブが欲しければ claude-code を進み、OpenAI ネイティブが欲しければ codex を進む。モデルを換えて遊びたいときに初めて、OpenHands の番が来る。Skill の冒頭が、この選択問題をあなたの代わりに解いてくれている。これが第一の細部だ。良い Skill は、それを「いつ使うべきでないか」を教えてくれる。

次に見ると、その工学化の程度こそが本当に恐ろしいところだ。その肝心な設計をいくつか挙げる。

| 設計 | 具体的なやり方 | なぜ模範なのか |
|---|---|---|
| 本物の flag 表 | 使えるパラメータの表を出し、「verified against openhands --help, CLI 1.16.0（openhands --help に対して検証済み、CLI 1.16.0）」と明記 | 記憶で適当に書いたのではなく、ヘルプドキュメントと一項目ずつ突き合わせてある |
| 負のリスト | 存在しない flag を明示する（`--model` / `--max-iterations` / `-workspace` / `--sandbox` はない） | 呼び出し側に「これらを試すな、試しても間違いだ」と自ら伝え、一往復分の試行錯誤を省く |
| 一段まるごとの Pitfalls | LiteLLM のノイズの warning、バナーの氾濫、model slug は provider のものではなく LiteLLM のものであること、`pip install openhands-ai` で入るのは間違ったパッケージであること（あれは legacy の V0） | 踏んだ落とし穴を全部書いてあり、後から来る者は直接避けて通れる |
| プラットフォームのゲート | [linux, macos] のゲート。OpenHands の上流は Windows では WSL が必要 | 非互換のシステムではこの Skill はそのまま姿を消し、インデックスを汚さない |

呼び出し方も抑制が利いている。terminal ツール経由で、`openhands --headless --json --override-with-envs --exit-without-confirmation` の一行を headless で呼ぶ。派手な封入はなく、コマンドラインを正しく叩き、落とし穴をはっきり示すだけだ。

良い Skill の判定基準は、それがどれだけ「何をすべきか」を書いたかではない。どれだけ「何をしてはいけないか」を書いたかだ。負のリスト、Pitfalls、「いつ私を使うな」。この3つこそが、一つの文書を「正しく見える」から「動かして本当に正しい」へ変える分水嶺である。正しい手順だけを並べた Skill は、実戦を経ていない取扱説明書に等しい。

ここには、この節の肝心な転換も隠れている。Skill はもはや「agent に読ませる知識」だけではない。外部 CLI への封入にもなり得る。OpenHands の Skill は本質的に薄い糊の層だ。agent の意図を、別の agent が理解できるコマンドラインに翻訳する。Skill の境界は、静かに押し広げられた。

### 進化する Skill：darwinian-evolver

他の agent を編成するのは一つの遊び方で、Skill にものを最適化させるのは別の遊び方だ。optional の research ディレクトリには darwinian-evolver があり、Imbue がオープンソース化した darwinian_evolver（LLM 駆動の進化探索ループ）を薄く封入している。

使い方はこうだ。あなたが適応度関数（fitness 関数、つまり採点器）を一つ与えると、それは進化の方法で何らかの成果物（artifact）を最適化する。一段のプロンプトでも、一つの regex でも、一文の SQL でも、小さなコードでもいい。一群の変異体を生成し、採点し、高得点のものを残し、また変異させる。一巡ごとに坂を登っていく。

これは Hermes 内蔵の自己進化とは別物だと、はっきり区別しておく必要がある。内蔵の自己進化が変えるのは Skill ライブラリそのものだ。darwinian-evolver が変えるのは、あなたの手元にある「採点器のあるもの」なら何でも、である。一つは内向き、一つは外向きだ。言ってみれば、この山登り法（hill-climbing）に独立した判定と進化の木を組み合わせる発想は、私自身が作った darwin skill と同源である。客観的なスコアを一つ与え、機械に世代を重ねて自ら登らせる方が、人手で調整するより安定する。

もう一つ、私が評価する細部がある。上流に対するライセンスの隔離がきれいなのだ。Imbue のあのライブラリは AGPL-3.0 で、この Skill は subprocess 経由でそのコマンドラインを呼ぶだけにし、上流のクラスを import しないよう意図的に避けている。これで「呼び出し」であって「結合」ではなくなり、伝染性のあるライセンスとの境界がはっきり引かれる。ライセンスの友好的でない外部依存と、Skill がどう付き合うべきか。これはその模範例だ。

### ここまでのまとめ

この節を一歩引いて見直そう。前では、Skill がどう作られ、どう改善され、オープン標準にどうただ乗りして来たかを語った。ここまで来て、Skill はその第二の顔を現した。それは知識であるだけでなく、agent 同士が互いを呼び出し合うためのインタフェースでもある。

一つの Skill が「別の agent を呼ぶ」封入であり得るとき、面白い問題が浮かんでくる。Hermes が Claude Code を指揮できるなら、同時に agent の群れを指揮し、分業と並行作業をさせることもできるのではないか。指揮棒を握った後の次の一歩は、当然、編隊である。

これこそが後ろの Part 6 で展開することだ。delegate_task が隔離されたコンテキストのサブ Agent を一つ派遣するところから、Kanban のボードの上で agent の群れが並んでタスクを引き受けるまで。Skill は「割り振り」という仕事を呼び出し可能にし、マルチ Agent の編成はそれを規模化可能にした。この節は、その章への序章である。
