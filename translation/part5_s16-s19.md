## §16 約90のツールとオンデマンド開示

README には「40+ tools」と書いてある。6月に私がソースを数えたら64個、10月に同じ数え方で数えたら88個だった。この差は、単なる数え方の口径の違いではない。その裏には、もっと面白い設計が隠れている。ツールが増えれば増えるほど、全部をまとめてモデルに渡してはいけない、という設計だ。

### まず数字をはっきりさせる

旧版の本では、Hermes には「40以上のツール」があると書いた。あれは公式 README の対外的な口径だ。6月に前版を書いたとき、私はソースをめくって registry の登録項目を数えた。本当にモデルから呼び出せるツールは64個で、spotify の一式のようにプラグイン経由で登録されるものまで入れると、およそ71個だった。10月のこの版では、もっと確実な数え方に変えた（一時的な環境を作り、ツールモジュールを読み込んでから registry を読む）。まず v0.16.0 で71を再現し、同じ数え方で v0.22.2 を数えると88個だった。公式のツールリファレンスには「約100個」とある。Kanban や元宝（Yuanbao、テンセントの AI アプリ）、デスクトップ GUI のように、特定の場面でしか現れないツールまで数に入れているからだ。

数字が合わないのは、2つの概念が混ざっているからだ。まず切り分けよう。

> **推奨**
>
> ツール（tool）: モデルが実際に call できる、その関数そのもの。例えば `web_search`、`terminal`、`image_generate`。v0.22.2 には88個ある。

> **非推奨**
>
> ツールセット（toolset）: ツールをグループ化してまとめた別名。例えば web = {web_search, web_extract}。こちらは約50個。

なぜ2層に分けるのか。「モデルに何を見せるか」と「機能ごとにどう整理するか」は別の話だからだ。ツールは原子で、ツールセットはセットメニューだ。後で分かるが、この階層化こそが「オンデマンド開示」の土台になっている。

### 5つのカテゴリ、ツールの全景

これらのツールを職能で分類すると、Hermes が何をできるかが見えてくる。私は toolsets.py と各ツールファイルを読んで、5つのカテゴリに分けた。

| カテゴリ | 代表ツール | 能力 |
|---|---|---|
| 実行系 | terminal、execute_code、read_file、patch、computer_use | コマンドを走らせ、ファイルを読み書きし、コードを直す。computer_use はバックグラウンドでデスクトップを操作し、あなたのマウスは奪わない |
| 情報系 | web_search、web_extract、browser_*（12個）、x_search | Web を検索し、内容を抽出し、ブラウザを開く。browser が大物で、サブツールだけで12個ある |
| メディア系 | image_generate、video_generate、video_analyze、text_to_speech | 画像を作り、動画を作り、動画を見て、音声を合成する。どれも、見せる入口は統一された1つだけ |
| 記憶・計画系 | memory、skills_list、todo_list、cronjob_manage、session_search | セッションをまたぐ記憶、Skill の管理、TODO、定時タスク、履歴をめくる |
| 調整系 | delegate_task、kanban_*（15個） | サブ Agent を派遣し、Kanban で Agent の群れを調整する（mixture_of_agents はもうツールではなく、任意で選べる仮想モデル moa になった） |

ここで1つ、拾っておく価値のある細部がある。旧版の本の記述には、もう古くなったものがある。旧版では調整系について「最大で並行3つのサブ Agent、最大3層」と書いた。今はデフォルトの並行数は10個（`delegation.max_concurrent_children`）で、ネストの深さはデフォルト1層、つまりフラットな派遣だ。多層にしたければ `max_spawn_depth` を自分で調整する。サブ Agent ごとに、250ラウンドの上限が別にある。サブ Agent はバックグラウンドで走らせることもでき、走っている最中に方向を変えたり、止めたりもできる。旧版では「rl ツール」という分類も挙げていたが、今は RL 環境は独立したディレクトリにあり、Agent のツール面には一切入らない。本を書くときに旧バージョンの制限値を引用すると、簡単に間違える。これは私がソースを読むときに踏んだ落とし穴だ。

### 肝心なのは数ではなく、「現れるべきときにだけ現れる」こと

64個のツールを、会話のたびに全部の定義を system prompt に詰め込んだら、どうなるか？

コンテキストが、ツールの定義で膨れ上がる。モデルは仕事を始める前に、ツールの説明書を読むだけでコンテキストの大きな塊を使い切ってしまう。もっと悪いことに、ツールが増えると、モデルが間違ったツールを選ぶ確率も一緒に上がる。

Hermes の解法は、2層のゲートだ。第1層がツールセットによるグループ化、第2層が progressive tool disclosure（段階的なツール開示）だ。まず第1層から話す。

多くのツールは、無条件には現れない。`check_fn` というゲート関数を持っていて、実行時の条件を満たしたときだけ、モデルから見えるツール一覧に入る。実際の例をいくつか挙げれば、この設計の抑制ぶりが分かる。

check_fn ゲートの実例: computer_use は、デスクトップドライバが入っているときだけ現れる。Kanban の十数個のツールは、Kanban のスケジューラに派遣されたときだけ現れる（§07 で worker が呼んだ kanban_show、kanban_complete がそれだ）。x_search は、xAI のログインか key がなければ現れない。入っていない、設定していない、発動していないものは、モデルにはそもそも見えない。6月版で私が挙げた send_message（Gateway が起動したときだけ現れる）は、後に丸ごと削除された。Home Assistant と Spotify の一式もコアから出て、プラグインディレクトリからインストールする形に変わった。

もう1つ、設計がうまいと思う安全面の絞り込みがある。webhook の場面だ。誰かが PR を出す、コメントを付ける、といったことで Hermes が起動する場面では、内容が信頼できない第三者から来ている可能性がある。この場面で Hermes が出すのは、最も安全な4つのツール（検索、抽出、画像を見る、確認を求める）だけだ。ローカル実行の権限は1つも与えない。webhook の文章には prompt injection が隠れているかもしれず、モデルが騙されて terminal を実行したら終わりだからだ。脅威モデルを、そのままツール開示のルールに書き込んでいる。

### Progressive tool disclosure: OpenClaw から学んだ一課

第2層のゲートは v0.16.0 で入った progressive tool disclosure で、ツールは必要に応じて開示される。v0.22 では、それが「任意」から常態になった。

有効にすると、MCP ツールと非コアのプラグインツールは、モデルが見えるツール配列に直接は並ばなくなる。代わりに3つのブリッジツールが置かれる。`tool_search`、`tool_describe`、`tool_call` だ。モデルは必要になったら、自分で「どんなツールがあるか」を検索し、使い方を調べ、それから呼び出す。図書館が「全ての本を目の前に広げる」方式から、「検索台を1つ渡す」方式に変わったようなものだ。

モデルが何かをしたい → `tool_search` で使えるツールを検索する → `tool_describe` で使い方を調べる → `tool_call` で呼び出す

ここには、設計の分寸がよく出ているルールが2つある。1つは、コアツールは決して遅延させないこと。ソースの原文は「Always load means always load. No exceptions.（常に読み込むとは、常に読み込むということだ。例外はない）」。最もよく使う一群のツールは終始見えているべきで、遠回りはさせない。もう1つは、この仕組みがいつ有効になるかだ。6月の時点では閾値があり、遅延可能なツールがコンテキストの10%未満しか占めなければ空転していた。今のデフォルト `tool_search.enabled: auto` は実質的に常時オンで、遅延読み込みに設定されたツールが1つでもあれば有効になる。横にある5%という数字は、ツールカタログ自体が予算の最大で何割までを占めてよいか、という方だ。v0.22 では、約19個の利用頻度の低い組み込みツールが、デフォルトで遅延読み込みに変わった。computer_use、session_search、image_generate、定時タスク、デスクトップ GUI の一群だ。公式の数字では、デスクトップ版がモデルに送るツール説明は、13,367トークンから6,883トークンに減った。

この件は、§07 で見た利用明細の中でも目撃した。`hermes insights` のツールランキングに、tool_search、tool_describe、tool_call がそれぞれ1回ずつ出ていた。私が「平日の朝9時にリマインドして」と言ったときのことだ。定時タスクのツールはデフォルトでは目の前に無く、まず検索し、使い方を調べ、それから呼び出していた。今は tool_call 1回で、最大10個のツールまでまとめて呼べる。

最も面白いのは、ソースのコメントに書かれた一文だ。このツールカタログはステートレスで、ターンごとに再構築される。なぜキャッシュしないのか。OpenClaw の教訓を、明確に学んだからだ。

> **注意**
>
> OpenClaw はかつて落とし穴を踏んだ。ツールカタログをセッション単位でキャッシュした結果、キャッシュとリアルタイムのツール登録表がずれて（ドリフトして）、ツールが静かに消えた。ユーザーはそのツールがまだあると思っているのに、モデルには見えず、しかもエラーにもならない。Hermes のコメントはこの回帰バグを名指しで引用し、同じ落とし穴を避けるために、ターンごとの再構築を選んでキャッシュしないとしている。

私はこういう「他人が転ぶのを見たから、この石を避ける」という工学的なコメントが特に好きだ。抽象的なベストプラクティスではなく、一手の、血の通った経験だ。この progressive disclosure は本質的に、Anthropic の「ツールは必要に応じて読み込む」という考え方のオープンソース実装で、MCP をたくさんつないだ後にコンテキストがツールの定義で膨れ上がるという、現実の問題を解いている。

### ツールの提供は全面的にプラグイン化: 1ファイル1バックエンド

「ツールをどう見せるか」を話したので、次は「ツールそのものをどう提供するか」だ。6月版の Hermes の最大のアーキテクチャ変更は、外部の能力をすべてプラグインにしたことだ。

web、browser、image_gen、video_gen の4カテゴリは、すべて plugins ディレクトリ配下の「1ファイル1バックエンド」に分解された。新しい画像生成サービスを足したい？ フォルダを1つ足せばいい。メインのツールを fork する必要はない。これはソースの言う「4方向のアーキテクチャ統一」で、4種類の外部能力が同じプラグインの骨格を共有している。

画像生成が一番分かりやすい。あなたが見ているのは `image_generate` というツール1つだけだが、背後には provider のディレクトリが一列に並んでいる。6月は5つ、v0.22.2 では8つ。deepinfra、fal、krea、meta-ai、openai、openai-codex、openrouter、xai だ。具体的にどれを使うかは、設定と可用性で自動的にルーティングされる。動画生成も同じで、`video_generate` という入口1つの背後に、今は deepinfra、fal、openrouter、xai の4つのバックエンドがある。テキストだけ渡せばテキストから動画を、テキストと画像を渡せば画像から動画を作る。v0.17 からは image_generate も、画像から画像を作れるようになった。Web 検索のプラグインはもっと多く、Brave、DuckDuckGo、Exa、Firecrawl、Perplexity、SearXNG、Tavily、xAI など十数個のバックエンドがある。

6月に数えたとき、FAL のルート1本から入ってくる画像生成モデルだけで12個あった（この数は動的で、Portal のドキュメントには今は9個と書いてある）。顔ぶれはかなり豪華だ。FLUX 2 Pro、Nano Banana Pro（つまり Gemini 3 Pro Image）、GPT Image 2、Z-Image、Qwen Image が揃っている。ソースはさらに細やかで、サイズの仕様を3つの族に分け、各モデルにはそのモデルが対応するパラメータキーだけを受け取らせ、拒否されるキーはそもそも渡らないようにしている。

### Krea 2 と xAI: プラグイン化が連れてきた2つの新顔

プラグイン化の最も直接の恩恵は、新しい能力が入ってくる速さだ。第1版には全く無かった2つの顔ぶれは、どちらもこの骨格で接続された。

1つは Krea 2。独立したネイティブプラグインがあり、FAL 経由でも使える。両方の道が通っている。Krea の API は非同期だ。送るとタスク ID が返ってきて、プラグインが2秒ごとに結果をポーリングし、外向きには同期呼び出しのように見せかける。ソースには価格と速度のメタデータも入っている。Krea 2 Medium はおよそ15〜25秒で画像を出し、強みはイラスト、アニメ、絵画といった表現的なスタイルだ。こういう、第三者の非同期 API を同期ツールに包む仕事こそ、プラグインの骨格がやるべき裏方の仕事だ。

もう1つは、もっと大げさで、xAI だ。これは普通の provider ではない。ログイン、検索、画像生成、動画生成、音声を横断するワンストップのサービスだ。

| xAI が持ち込んだ能力 | 具体的に何か |
|---|---|
| SuperGrok OAuth ログイン | API key は不要、サブスクリプションをそのまま使える |
| x_search | X の投稿とスレッドを検索する |
| Web Search provider | Brave、Tavily と並ぶ検索バックエンドの1つ |
| grok-imagine 画像生成 | image_gen プラグインの中に接続されている |
| Grok Imagine 動画生成 | テキストから、画像から、参照画像による誘導も対応 |
| Custom Voices TTS | 音声合成に音声クローンを追加 |

私は、xAI のこの線は特に味わい深いと思う。これは「オープンソースの Agent が、閉鎖的な大手企業1社のサブスクリプション能力を、余すところなく使い切る」標本だ。SuperGrok を契約していれば、Hermes がその契約の検索、画像生成、動画生成、音声を全部使えるようにしてくれる。API key を何個も別々に設定する必要はない。

ただし、工学的な細部で Nous のために一言言っておきたい。彼らは手を抜いていない。x_search の戻り値には `degraded` というフィールドが足されている。アカウントや日付のフィルターを付けたのに引用元が1つも取れなかったとき、`degraded=true` と印が付く。「この答えはモデルが自分で作ったもので、X のインデックスから来たものではない」と告げるのと同じだ。「本当の情報源があるかどうか」をツールの戻り値に組み込む。この誠実さは、なかなか得がたい。

### この節が言いたいこと

冒頭の「88対40」の差に戻ろう。あれは実は、節全体の比喩だ。ツールの増加は本物だが、増加そのものが負担にもなる。Hermes の答えは、「能力が多い」ことを「全部モデルに見せる」ことと直結させないことだ。ツールセットのグループ化、check_fn のゲート、progressive disclosure、プラグイン化した提供。この4つを貫くと、1つの統一した態度になる。能力はいくらでも伸びてよい。だが、各時点でモデルに見せるのは、そのとき、その場所で本当に役に立つ、ほんの一握りだけだ。OpenClaw が、ツールが多すぎて精度を落とした落とし穴を、Hermes はこの仕組みで避けた。

次の節では、外部世界とつながるもう1つの大動脈、MCP を見る。Hermes は MCP で2つの方向をやってのけた。思っているより回りくどい話だ。

## §17 MCP の2つの方向

ほとんどの人が理解している MCP は一方向だ。自分の Agent に、他人のツールを呼ばせる。Hermes はこれを双方向にした。公式ストアを巡ってワンクリックでプラグインを入れるクライアントであると同時に、Claude Code や Cursor から逆に呼び出されるサーバーでもある。同じプロトコル、2つの方向。これは第1版以降で最も語る価値のある変化の1つだ。

### まず「方向」ということをはっきりさせる

MCP は接続プロトコルで、Agent と外部ツールがどう対話するかを定めている。ほとんどのチュートリアルは1つの方向しか語らない。あなたの Agent が client として外部の MCP server につなぎ、そのツールを持ってきて使う、という方向だ。

それは間違いではないが、半分しか語っていない。プロトコルには両端があり、Hermes は両端を押さえた。

もっと生活感のある例えを使おう。MCP は USB-C の口のようなものだ。あなたのコンピュータは USB メモリを挿してデータを読み（host になる）、別のコンピュータに挿されて外付けドライブとして読まれる（device になる）こともできる。Hermes は host であり、device でもある。外部の MCP server を呼べるし、自分が MCP server になって、他の Agent に呼ばせることもできる。

| 方向一: Hermes が client | 同じ MCP プロトコル | 方向二: Hermes が server |
|---|---|---|
| 外部 server を呼ぶ | ↔ | 他の Agent に呼ばれる |

この2つの方向を分けて語り、間に挟まる3つ目の話、公式の審査済みカタログについても語る。

### 方向一: Hermes が client として外部 server を呼ぶ

これは旧バージョンからある能力だが、土台はしっかり作り込まれている。ソースを読むと、3つのトランスポート（転送方式）に対応していて、server の3つの配置形態に対応している。

| トランスポート | どこで動くか | 典型的な場面 |
|---|---|---|
| stdio | ローカルの子プロセス | このマシンに入れたツール。プロセスを起動して標準入出力で対話する |
| HTTP（StreamableHTTP） | リモートサービス | Linear のように自前のサービスを持つ製品など、クラウドでホストされる MCP |
| SSE | リモートサービス（ストリーミング） | サーバー側から継続的なプッシュが要る、長く続く接続の場面 |

設定は `~/.hermes/config.yaml` の `mcp_servers` に書く。接続すると、外部 server のツールは Hermes 自身のツール表に登録され、モデルがそれを呼ぶのは組み込みツールを呼ぶのと何ら変わらない。この点が肝心だ。モデルにとっては、「web_search」と、どこかの外部 MCP がくれたツールは同じ姿をしていて、ツールがどこから来たかを知る必要はない。

server ごとに細部の設定もできる。タイムアウト、この server のツールを並行して呼んでよいか、Bearer 認証ヘッダーを付けるか、server 側から LLM へのリクエストを開始してよいか。これらは全部、実運用のための調整用のネジだ。

本当に凝っているのは OAuth の部分だ。Hermes は MCP の OAuth 2.1 のハンドシェイクを完全に実装している。動的クライアント登録（DCR）、PKCE、トークンの自動更新が全部ある。つまり Linear のような自前 OAuth を持つリモート MCP は、ローカルに何も入れる必要がなく、Agent が初めて呼ぶときに自動で認可フローを回し、トークンを取り、期限が切れたら自動で更新する。「ログインが要る外部サービスにつなぐ」という面倒な仕事を、ユーザーがほぼ意識しないところまで持っていった。

### 間に挟まる話: 「自分で探す」から「公式ストア」へ

旧バージョンで MCP をつなぐには、隠れた敷居があった。自分で GitHub に行って信頼できる MCP server を探し、そのドキュメントを読み、自分で config を書かなければならない。探し間違えた、設定を間違えた、問題のある server につないだ、そのリスクは全部あなた持ちだった。

新バージョンはこの隙間を埋めた。やり方は、Nous 公式の審査済みカタログを作ることだ。形は Skill のカタログと同じで、`hermes mcp` と打てば対話式のセレクタに入り、1つ選んでワンクリックで入れられる。必要な認証情報はインストール時に促されて入力し、自動でローカルの `.env` に書き込まれる。

「カタログにある＝審査済み」: この公式カタログに入る MCP は、どれも PR レビューを経て取り込まれたものだ。Nous があなたに代わって信頼性の選別を1回やってくれるのと同じで、見知らぬ GitHub リポジトリが安全かどうかを賭ける必要はもうない。

ここは事実に即して言わなければならない。私は「MCP で Hermes が6,000以上のアプリに接続できる」と言う資料を見たことがあるが、この数字は v0.16.0 と v0.22.2 のソースにもリリースノートにも、一次の出典が見つからなかった。そうは書けない。正確な口径は2文だ。

第1に、能力の面では、Hermes は任意の MCP server に接続できる（stdio／HTTP／SSE の3つとも可）。README の原文は「Connect any MCP server」。理論上は、MCP エコシステム全体に接続できる。

第2に、公式審査済みカタログ（optional-mcps）の規模だ。6月に前版を書いたとき、収録は2つだけだった。Linear（リモート HTTP＋ネイティブ OAuth）と n8n（ローカル stdio のブリッジで、11のツールを公開し、デフォルトでは読み取り専用の8つだけがオン）。4か月後、このカタログは65個に育った。Airtable、Asana、Atlassian、Cloudflare、Figma、GitHub、Linear、Notion、Sentry、Stripe、Supabase、Vercel が入っている。§08 で見たブラウザパネルの MCP ページがそれで、項目ごとに INSTALL ボタンが1つ付いている。

当時私がわざわざ褒めたあの n8n ブリッジは、逆に取り下げられた。すでに入れた人は使い続けられるが、カタログではもう提供されず、n8n-official に置き換わった。n8n 公式の HTTP インターフェースに直結し、ブラウザの OAuth でログインする。ローカルのブリッジも API key も要らない。この置き換えの方向は Linear と一致している。相手の公式ホスト型 MCP が使えるなら、ローカルでブリッジを保守しない。

入れ方も楽になった。コマンドラインには、カタログを見る `hermes mcp catalog`、入れる `hermes mcp install linear` がある。会話の中でそのまま「Linear の MCP をつないで」と言えば、設定カードがポップアップする。デスクトップ App ではダイアログ、コマンドラインではパネルだ。ログインが要るものはブラウザ認可を通り、v0.22 ではデバイスコードログイン（`hermes mcp login サービス名 --flow device`）も加わった。ブラウザの無いサーバーで使うのに向いている。

さらに1段上がって、v0.22 はデスクトップ App の MCP ページを Connectors ページに変えた。ホスト型のアプリ接続（Linear、Notion の類で、チャットで一言言ってブラウザで1回ログインすれば使え、Nous のアカウントも要らない）と MCP が1つの一覧に統合され、同じサービスに複数のアカウントをぶら下げることもできる。仕事用と個人用を1つずつ、といった具合だ。コマンドラインでは `hermes connectors`、会話では `/connectors` が対応する。

### 方向二: Hermes が自分を MCP server として公開する

これは最も見過ごされやすく、私が最も面白いと思う方向だ。

`hermes mcp serve` と1行打てば、Hermes は stdio の MCP server を起動する。このとき Hermes はツールを呼ぶ側ではなく、呼ばれる側だ。Claude Code、Cursor、Codex のように、それ自身が MCP client であるツールが、逆に Hermes を外部ツールとして使える。

何の能力を外に公開するのか。ソースで数えると10個のツール（v0.22.2 でも10個で、一覧は少し入れ替わっている）。「セッション」を巡るものだ。現在の全セッションの一覧、あるセッションのメッセージ履歴と添付ファイルを読む、セッションにメッセージを送る、新しいイベントをポーリングして待つ、承認待ちのリクエストを見て応答する、それに全チャンネルの一覧を出すツールが1つある。これらの操作はプラットフォームを横断する。Telegram、Discord、飛書（Feishu）でつないだ全セッションに、この1つの MCP インターフェースから統一してアクセスできる。

人間の言葉に翻訳すると: Claude Code の中から、Telegram での Hermes との会話を直接読んで返信できる。Hermes は「セッションの中枢」になった。他の Agent は MCP で接続すれば、Hermes が管理する一群のメッセージプラットフォームを操作できる。

> **ポイント**
>
> ソースのコメントには面白い一文がある。このインターフェース一式は「OpenClaw の9ツールの MCP ブリッジをベンチマークにした」もので、Hermes はチャンネル一覧ツールを1つ足して10個にしたという。これはオープンソース界隈で互いに学び合う常態だ。相手の良いインターフェースの形を見たら、それに倣ってもっと完全なものを作る。本を書くとき、こういう一次の細部は、空疎な「機能が強力だ」よりもずっと説得力がある。

### MCP を使うとき、ネイティブツールを使うとき

2つの方向を語り終えたら、実務的な問いに答える必要がある。Hermes では少なくない外部製品（飛書の類や、6月の時点の Spotify、Home Assistant。今この2つはプラグインディレクトリに移った）が、MCP を通さずネイティブツールやプラグインとして直接書かれている。一方で Linear、n8n は MCP を通っている。同じ外部サービスの接続なのに、なぜあるものはネイティブで、あるものは MCP なのか？

ソースの取捨から、私はおおよその判定基準を1つ帰納した。

> **推奨**
>
> MCP を使う: ① そのサービス自体が既に公式の MCP server を提供している（Linear が自前のリモート MCP を持っているような場合。つなげば済むのに、なぜ書き直すのか）; ② つなぎたいのが「任意」の第三者で、数が無制限。一つ一つネイティブツールは書けない; ③ ツールセットが頻繁に変わる。server 側に保守を任せる方が楽だ。

> **非推奨**
>
> ネイティブツールを使う: ① その統合を Hermes が深く作り込み、最高の体験にしたい場合（Spotify の7つのツールは再生／デバイス／プレイリストを覆い、MCP ブリッジより手になじむ）; ② Hermes の内部機構と密に結合する必要がある場合（飛書のドキュメントがメモリシステムと連携するような場合）; ③ 呼び出し頻度が高く、遅延に敏感で、MCP プロトコルのオーバーヘッドを1層減らしたい場合。

結局のところ、MCP は「広さ」の解法で、ネイティブツールは「深さ」の解法だ。多く、雑多に、他人が既に作ったものにつなぐなら MCP。精密に、深く、体験を自分で握りたいなら、ネイティブツールを書く。Hermes はどちらの道も残している。これは二股をかけているのではなく、異なる需要でそれぞれの長所を取っているのだと思う。

もう1層の考慮は、前の節で語った progressive tool disclosure の中にも隠れている。MCP をたくさんつなぐと、数十から百あまりのツールの定義が、モデルのコンテキストを膨らませる。だから Hermes は MCP ツールについて、デフォルトで「オンデマンド開示」を通す。モデルに全部を直接並べず、まず検索させてから呼ばせる。

これで、なぜ全てを MCP に詰め込んではいけないかも説明が付く。コアで高頻度な能力はネイティブツールにして常駐させ、周辺のロングテールな能力は MCP でオンデマンドに読み込む。2つの仕組みを組み合わせて使うことで、コンテキストがツールの定義に食い尽くされることがなくなる。

次の節ではツール層を離れて、Hermes の接続のもう1つの次元を見る。今や20あまりのプラットフォームであなたと会話できること、そしてそれらを縫い合わせている Gateway 自体が、自分で育つようになったことだ。

## §18 20あまりのプラットフォームと、自分で育つ Gateway

4月の第1版では「6つの一級プラットフォーム、統一された Gateway プロセス」と書いた。6月の第2版では、公式の口径で「23のメッセージプラットフォーム」。10月になると、公式は整数を出すのをやめた。本当に変わったのは、実は数字ではない。新しいプラットフォームを足すやり方が、「コアのコードを書き換える」から「ディレクトリにフォルダを1つ放り込む」に変わったことだ。

### 繰り返し唱えられる、あの数字について

Telegram、Discord、Slack、WhatsApp、Signal、SMS、メールから、釘釘（DingTalk）、飛書（Feishu／Lark）、企業微信（WeCom）、微信（WeChat）、QQ、騰訊元宝（Tencent Yuanbao）、さらに Microsoft Teams、Google Chat、LINE、Matrix、Home Assistant、6月の時点の23番目だった ntfy、それから後に加わった iMessage（Photon 経由）、Raft、WhatsApp 公式ビジネスインターフェース（この3つは v0.17）、そして Buzz（v0.20）。思い付く主な IM は、Hermes がほぼ全部、その「顔」になれる。

まず、この数字の幻想を剥がしておきたい。6月の時点で、公式には確かに整数があった。「23のメッセージプラットフォーム」で、v0.15.0 のリリースノートの「ntfy as the 23rd messaging platform（ntfy が23番目のメッセージプラットフォーム）」という一文が出所だ。ただ、口径はずっと少し揺れていた。公式ドキュメントはブラウザも数に入れ、ソースには他にも IRC、API Server、Webhook といった接続チャネルが転がっている。

v0.22.2 になると、公式ドキュメントのトップには「20+ platforms」とあり、メッセージ Gateway のページの能力比較表には27行が並び、私が §08 で撮ったブラウザパネルでは、チャットチャンネルのページに「0 of 32 channels configured（32チャンネル中0を設定済み）」と出ていた。同じバージョンで、3か所で3つの数字だ。数えているものが場所ごとに違うからだ（webhook を入れるか、Agent 用の A2A のようなチャネルを入れるか）。だからこの版では「20あまり」とだけ言い、正確に言うなら、どこの数字かを明示する。

これらのプラットフォームは一括で生えたのではなく、少しずつ育った。6月より前は、公式が1つずつ「何番目」と番号を振っていて、タイムラインははっきりしている（下の表はその時代のもの。その後、公式は番号を振らなくなった）。

| プラットフォーム | 入ったバージョン | 公式の数え方 |
|---|---|---|
| Google Chat | v0.13.0（2026.5.7） | 20番目 |
| LINE + SimpleX Chat | v0.14.0（2026.5.16） | 累計22まで |
| Microsoft Teams（エンドツーエンドで開通） | v0.14.0（2026.5.16） | — |
| ntfy | v0.15.0（2026.5.28） | 23番目 |

4月から6月の2か月で、会話できるプラットフォームが5つ増え、6月から10月にも5、6個増えた。第1版の本の頃には「第N個」という公式の数え方自体が無く、6つの一級と9つの二級拡張とだけ書いた。数字の膨張そのものは大したことではない。肝心なのは、膨張のコストが一緒に上がらなかったことだ。それがこの節が本当に語りたいことだ。

### 「コアを書き換える」から「フォルダを放り込む」へ

旧版の本のあのバージョンでは、プラットフォームを1つ足すのは、かなり重い仕事だった。コアのコードに行って、if/elif の分岐を何か所も書き換える。メッセージが入ってきたら、どのプラットフォームから来たかを判定し、出ていくときは、どのプラットフォームへ送るかを判定し、設定の解析、ユーザーの認可、状態の表示、どこも新しいプラットフォームのために1行書き換える必要があった。プラットフォームが増えるほどコアは膨れ上がり、1か所直せば別の場所を壊さないかと心配になる。

v0.16.0 のやり方は違った。コアには PlatformRegistry という登録表（レジストリ）がある（`gateway/platform_registry.py` の中だ）。これはシングルトンで、プラットフォームを足したい者は、この登録表に自分を登録する。Gateway はメッセージを受け取ると、まず登録表を調べ、見つからなければ古い組み込みの経路にフォールバックする。

新しいプラットフォームは、もうコアには書かれず、`plugins/platforms/` ディレクトリに住む。1プラットフォームに1フォルダで、中に `plugin.yaml` と `adapter.py` が入る。プラグインは起動時に `ctx.register_platform()` を呼んで、自分で登録する。

新しいフォルダを作る → adapter + plugin.yaml を書く → Registry に自己登録する → コアのコードは1行も変えない

公式ドキュメントの一文は、とても直截だ。プラグインの経路は「requires zero changes to core Hermes code（コアの Hermes コードへの変更はゼロで済む）」。adapter の作成、設定の解析、ユーザーの認可、cron の配信、メッセージのルーティング、システムプロンプト、状態の表示、インストールウィザード。この一式全部を、プラグインシステムが自動で引き受ける。

では、1つのプラットフォームは Registry に対して、結局何を明らかにしなければならないのか。それが PlatformEntry というデータ構造の仕事だ。「Gateway が1つのプラットフォームを認識するのに必要な全て」を、宣言的なフィールドの一覧にしたものだ。面白いものをいくつか拾うと、設計者がどれだけ細かく考えているかが感じられる。

| フィールド | それが解く問題 |
|---|---|
| max_message_length | そのプラットフォームの1通の最長。超えたら自動で賢く分割する |
| pii_safe | セッションの説明をマスキングするかどうか（SMS の電話番号を平文で表示しない、など） |
| platform_hint | システムプロンプトに差し込むプラットフォーム向けの指示。例えば Agent に「今あなたは IRC にいる。markdown は使うな」と告げる |
| standalone_sender_fn | cron タスクと Gateway が同じプロセスに無いとき、一時的に接続を開いてメッセージを送り出す |
| apply_yaml_config_fn | プラグイン自身に自分の設定を解析させ、コアの config.py が各プラットフォームのスキーマを理解しなくて済むようにする |

最後のフィールドを見れば、設計全体の用心が分かる。コアのコードは意図的に自分を「鈍く」している。各プラットフォームの設定がどんな形をしているかを、あえて理解しようとしない。理解するかどうかはプラグイン自身の仕事だ。コアは「プラットフォームが1つ登録された。その宣言したルールに従って処理する」だけを担う。プラットフォームの複雑さは各自のフォルダの中に閉じ込められ、コアに染み出ることはない。

この線は、この本の主線「手綱が自分で育つ」と響き合う。Agent の能力は自分で育ち（Skill の自己改善）、その接続層も自分で育っている。プラットフォームが1つ増えても、コアは毛筋一本動かない。Gateway は「プラットフォームを山ほど組み込んだ大きなプロセス」から、「登録表を持つプラットフォームのホスト」へと育った。

細部が1つ。6月の時点で、Discord、Home Assistant、Mattermost のいくつかは、古い組み込みの列挙にも、新しいプラグインディレクトリにも同名のものがあった。歴史的な組み込みプラットフォームが、1つずつプラグインへ移行している痕跡だ。v0.22 ではこの件は、ほぼ移行が終わった。v0.18 から、Slack、釘釘、WhatsApp、Matrix、飛書、Telegram、企業微信、メール、SMS はパッケージ同梱のプラグインに変わり、Home Assistant はプラグインディレクトリに移って、別途インストールする形になった。互換の経路は残っている。登録表で見つからなければ、古い経路にフォールバックする。

### プラットフォームが増えるほど、起動は速くなる

常識で言えば、プラットフォームが増えるほどプロセスの起動は遅くなるはずだ。立ち上げるものが増えるのだから。Hermes は逆を行く。

秘訣は遅延読み込み（レイジーローディング）だ。QQ と元宝の2つのアダプタは特に重い。元宝はリバースエンジニアリングで得た非公開プロトコルに WebSocket のスタックを重ねたもので、QQ はチャンク分割アップロード一式を立ち上げる。以前は CLI を呼ぶたびに、この2つが急いでインポートされ、それだけで約48ミリ秒と8MB のメモリを食っていた。しかも、今回あなたは QQ を使ってもいないのに、だ。

今は、使うときにだけ読み込む形に変わった。v0.14.0 がコールドスタートを約19秒削り、v0.15.0 が会話ごとの関数呼び出しを47%減らしたことと合わせると、Gateway 全体の性能の話は、かなり直感に反する一文になる。プラットフォームは増えるほど増え、起動は速くなるほど速くなる。

### 「Telegram で始めて、Discord で続ける」— この一文は直さなければならない

プラットフォームをまたぐ会話の継続性は、Hermes がずっと看板にしてきた売りだ。旧版の本では結論だけを書いた。Telegram で話の途中まで来て、Discord に移っても続きを話せる。魔法のように聞こえる。

だが私はソースをひと通りめくって、この一文を字面どおりに理解すると問題が起きることに気付いた。事情を知る読者が突けば、すぐにばれる。正確性の地雷にならないよう、本当の仕組みをはっきりさせなければならない。

第1層は、セッションの身元だ。ソースには「セッションの一意の身元」を生成する専用の関数があり、こんな姿をしている。

`agent:main:{platform}:dm:{chat_id}`
`agent:main:{platform}:{chat_type}:{chat_id}`

（真ん中の main はデフォルトの profile の名前だ。別の profile を作れば、ここは agent:<profile 名>: になる。）

注目してほしいのは、このキーがプラットフォーム名で始まっていることだ。つまり、同じ人間でも Telegram と Discord では、厳密には2つの異なるセッションになる。「文字どおり同じ1つの会話履歴を共有している」のではない。

では継続性はどこから来るのか。別の仕組み、ソースで session mirroring（セッションのミラーリング）と呼ばれるものだ。あるメッセージが、あるプラットフォームへ送られると、システムは送り先のセッションの会話記録に「ミラー記録」を1件追加し、受け取る側の Agent に、さっき何が起きて、何が送られたかを知らせる。

だから「プラットフォームをまたぐ継続」の体験を本当に支えているのは、3つのことの積み重ねだ。

**1. 同じ Agent、同じメモリと Skill の一式**

20あまりのプラットフォームが、同じ1つの Agent インスタンスを共有する。どのプラットフォームで言った好みも、同じ1つのメモリ庫に入る。プラットフォームを変えても、あなたへの理解がゼロに戻ることはない。

**2. プラットフォームをまたいでメッセージを送るとき、transcript をミラーする**

メッセージがプラットフォームをまたいで流れると、内容が送り先のセッションの記録にミラーされ、向こう側の Agent は文脈を持てる。きょとんとした顔にはならない。

**3. デスクトップ App は、profile をまたいでセッションを引用できる**

新しいデスクトップ App では `@session` で別のセッションを直接引用でき、出所の違う会話を串刺しにできる。

この層の仕組みをはっきりさせるのは、几帳面ぶるためではない。「同じセッションが途切れなく続く」という想像のまま使えば、境界の場面で困惑するからだ。「なぜときどき『忘れた』ように見えるのか」。「共有されたメモリ＋ミラーリング」という真相を理解してこそ、その能力の境界がどこにあるか分かる。

> **注意**
>
> この章を書くとき、私は踏みやすい落とし穴をいくつか、わざわざ挙げた。「Telegram で始めて Discord で続ける」を字面どおりに書き写さないこと。プラットフォーム数を整数で書かないこと。6月の「23」は今はもう正しくない。書くなら、どこの数字かを明示すること。GitHub の star のような変動の激しい数字は、量級だけを書き、日付を添え、固定しないこと。確かめられない対外的な主張は、保守的に、仕組みを書く方を選び、確かめていない数字は書かないこと。

### それが意味すること

この節を締めよう。プラットフォームの数字は表の顔で、登録表（レジストリ）が中身だ。

ある製品が「プラットフォームを足してもコアを変えない」ために専用の登録表の仕組みを設計しようとするのは、その製品が、プラットフォームの数はまだ増える、しかも長く増え続ける方に賭けているということだ。第30個、第50個のプラットフォームのときに、コアが書き換えで駄目になるのを避けたいのだ。これは未来への前払いだ。今、抽象化を1層多く書くことで、将来何度も訪れる「フォルダを放り込めば済む」気楽さと引き換える。

あなたというユーザーにとって、恩恵は直接的だ。あなたがつなぎたいニッチな IM を、公式が作っていなくても、コミュニティがフォルダ1つで補える。コアチームの予定を待つ必要も、プロジェクト全体を fork する必要もない。接続の口は、完全に開かれた。

次の節では、Gateway のもう1つの側面の進化を見る。ついに顔ができたのだ。ネイティブのデスクトップ App と、ブラウザの管理パネル。「後ろに隠れたプロセス」から、あなたが直接クリックできるものになった。

## §19 3つの話しかける姿勢

今年の春、Hermes を使いたければ、まずターミナルを開かなければならなかった。6月の v0.16.0（公式の代号は The Surface Release）で、デスクトップ App と、まともなブラウザパネルが生えた。10月の v0.22 では、デスクトップ版は初回起動で API key すら入力しなくてよくなり、ガイド付きの会話について行けば使えるようになった。この節で語るのは、あなたがどこから Hermes に話しかけるか、だ。

### まず、この節と前の節の違いをはっきりさせる

前の節が語ったのは Gateway の内側だ。20あまりのプラットフォーム、登録表、セッションをどう続けるか。あれは後ろ側の話だ。

この節が語るのは表側だ。あなたは結局、どこから Hermes に話しかけるのか。同じ脳、同じメモリと Skill の一式だが、今は3つの顔がある。私はこれらを3つの姿勢と呼ぶ。どの姿勢の裏にも、実は異なる使用習慣がある。

IM プラットフォーム → ネイティブのデスクトップ App → ブラウザの管理パネル

この3つの顔は排他的ではない。昼はデスクトップ App でコードを書き、夜はベッドに寝転んで Telegram で続きを話し、妻がブラウザパネルで設定を1つ変える、といったことができる。全部、同じ1つの Agent を指している。

### 姿勢一: IM の中で気軽に話す

これは Hermes の最も古く、最も象徴的な姿勢だ。安いクラウドホストに配置して24時間動かし続け、Telegram、Discord、飛書、微信から気軽にメッセージを送る。

この物語は旧版の本で書いたので、繰り返さない。その真髄は、Agent がクラウドに住み、あなたがどこへ行っても呼び出せることだ。地下鉄の中で、データをクロールしたくなったとする。携帯を取り出してメッセージを1つ送ればいい。コンピュータを開く必要も、VPN につなぐ必要もない。

問題も明らかだ。IM はチャットの枠だ。話しかけることはできるが、チャットの枠の中で Hermes を設定するのは不便だ。どのプラットフォームのキーを変えるか、どのツールを開くか、Hermes があなたの何を覚えているか。こういうことは、会話の吹き出しの中でやるには、とてもやりにくい。

それが、後の2つの顔が解くべきことだ。

### 姿勢二: ネイティブのデスクトップ App、しかもリモートに接続できる

6月の v0.16.0 の最大の見どころは、本物のネイティブのデスクトップ App だ。公式の言葉はかなり率直で、この品物は「1週間前には存在しなかった」。1週間で、100の PR と159回のコミットで作り上げたという。

これは Electron アプリだ。ファイルをチャットにドラッグする、クリップボードから画像を直接貼る、Cmd+K でコマンドパレットを呼び出す、ステータスバーでモデルをその場で切り替える。デスクトップ体験としてあるべきものは揃っている。

インストールパッケージについては、6月版の書き方が広すぎたので、v0.22 のインストール文書で訂正する。

| システム | どう入れるか | 注意点 |
|---|---|---|
| macOS | 公式サイトから DMG をダウンロード | Apple Silicon 版のみ。Intel Mac はデフォルトではパッケージが出ない |
| Windows | 署名済みの MSIX、または Microsoft Store から直接入れる | Windows 11 22H2 以上が必要。以前の NSIS／MSI インストーラは削除済み |
| Linux | 先にコマンドライン版を入れ、それから `hermes desktop` を実行 | リリースフローに Linux 用インストールパッケージは無い |

コマンドライン版を既に入れている人は、macOS と Windows では `hermes desktop` でデスクトップ版を追加で入れることもでき、両者は同じ `~/.hermes` を共有する。v0.22 では Simple と Advanced の2つのモードも加わった。Simple は高度な設定を全部隠すので、設定項目を見たくない友人に渡すのに向いている。私は今回デスクトップ版を入れてテストしていない。この段は、公式ドキュメントとリリースノートに基づいて書いている。

だが、本当に賢いところは「クライアントを作った」ことではない。このクライアントが、ローカルで Hermes を動かさなくてもいい、という点だ。

ノートパソコンのデスクトップ App を、リモートの Gateway に向けることができる。あなた自身の homelab、一台のホストされたマシン、チームメイトのサーバーでもいい。暗号化された WebSocket 接続を通じ、OAuth かユーザー名とパスワードでログインすればいい。後には SSH リモートモードも加わり、App の中からリモートマシンのファイルを直接閲覧できるようにもなった。

これは「薄いクライアント＋重い計算の分離」だ。ノートパソコンは軽い GUI を1つ動かすだけで、本当に計算を食い、あなたの API key を置いている重い Agent は、本来いるべき場所で動く。MacBook のファンは回らず、仕事はサーバーで片付く。

私はこの一歩が、旧版の本の物語に対するアップグレードだと思う。以前の標準的な遊び方は「5ドルの VPS＋Telegram」だった。安いクラウドホストで Agent を動かし、携帯をリモコンにする。今は、もっと手になじむ道が増えた。VPS で Gateway を動かし、デスクトップ App を体面のあるフロントエンドにする。

もう1層重ねる。各 profile は異なるリモートホストを指すことができ、1つのウィンドウで複数の profile のセッションを並行させ、profile をまたいで `@session` で別の会話を直接引用することもできる。1台のノートパソコンが、あなたの個人マシンと会社のマシンに同時につながり、互いに邪魔をしない。

6月以降、デスクトップ版にはさらに多くのものが生えた。Projects（プロジェクトごとにセッションとファイルをまとめる）、Connectors（チャットの中で Linear、Notion のようなホスト型アプリを直接つなぐ）、Bot Mode（数体の bot に名前とアバターを付け、1つのグループに引き入れて互いに話させる）、クリックして入って直せるメモリのグラフ。これらは §08 で簡単に触れたので、展開しない。

### 姿勢三: ブラウザの中の全機能の管理パネル

3つ目の顔はブラウザパネルだ。§08 で既に1ページずつ見て回った。それはかつての「セッションが見られるだけ」の粗末なページから、完全な管理バックエンドに育った。

核心の価値は一文だ。かつてサーバーに SSH で入って config.yaml を書き換えていたことが、今は Web ページで何回かクリックすれば済む。

| パネルのモジュール | 何ができるか | かつてのやり方 |
|---|---|---|
| Channels ページ | Web ページで各メッセージプラットフォーム（Telegram／Discord／Slack…）を設定 | SSH で config.yaml を書き換え |
| MCP catalog | Web でクリックして各 MCP server を有効化／無効化 | mcp_servers の設定を手書き |
| 認証情報と Webhook | キーを管理し、webhook と hook を作る | コマンドラインで1つずつ設定 |
| メモリと Gateway の制御 | メモリ設定を調整し、Gateway を制御し、ワンクリックで Debug Share | ログをめくり、手動で再起動 |

ログイン方式も差し替え可能で、OIDC かユーザー名とパスワードかを自分で選ぶ。v0.22 では、1台のマシンでパネルサービスは1つだけが動き、全 profile はサイドバーで切り替える。各 profile ごとにポートを開ける必要はない。

デフォルトでは 127.0.0.1:9119 だけをリッスンし、このマシンからしか開けない。公開ネットワークにバインドしたいなら、ログイン認証の設定が必須だ。認証を飛ばす以前の `--insecure` パラメータは、もう効かなくなっている。パネルをリモートで見たい場合、公式の推奨は SSH トンネルだ。

### ついでに: ACP、あなたのエディタの中へ潜り込む

3つの姿勢の他に、方向の少し違う第4の入口がある。単独で語る価値がある。

Hermes は ACP アダプタを作り、Agent Client Protocol を通じて、VS Code、Zed、JetBrains の中へ、バックエンドの Agent として接続できるようにした。エディタを奪うのではなく、エディタの背後にいる、取り替え可能な Agent になる。

この線の工学的な取捨は、とても面白い。エディタの場面では、Hermes は専用に切り詰めたツールセット `hermes-acp` を使い、メッセージを送る、音声を読み上げる、確認の吹き出しを出すといった、IM でこそ要る能力を削り落とし、コードを書くことに関わるものだけを残した。ターミナル、ファイルの読み書き、パッチ当て、ブラウザ、Skill、メモリだ。

だからエディタの中では、SMS は送らず、詩も読まず、ひたすらコードを書く。

接続のやり方は、この数か月で1回変わった。6月の時点では uvx でワンクリック導入ができ、Zed の ACP Registry にも収録されていた。7月に公式が pip／PyPI のインストール経路を削ったとき、この線も一緒に削除された。今のやり方は、まず §04 のとおりに Hermes を入れ、それからエディタにカスタムの agent server を1つ足す。コマンドには `hermes`、引数には `["acp"]` と入れる。Zed は設定でそう入れ、VS Code は ACP Client 拡張を入れてからそう入れる。

> **ポイント**
>
> 既に Claude Code や Cursor を使っているなら、ACP のこの線はこう理解できる。Hermes は、あなたのエディタの中の「取り替え可能な脳」になりたいのだ。エディタは変わらず、背後で働く Agent が Hermes に替わる。しかもその Agent は、プラットフォームをまたいであなたが蓄積したメモリと Skill を持っている。

### 16の言語と、完全な簡体字中国語

最後の変化は、中国語の読者には実質的な朗報だ。ローカライゼーションの次元は、今年の春にはゼロだった。6月に16言語のカタログが生え、v0.22 ではユーザーが目にする文字列は全て、同じ翻訳カタログを通るようになった。組み込みは16、7種の言語（リリースノートには16、ドキュメントには17とある）で、簡体字中国語と繁体字中国語がどちらも入っている。組み込みでない言語は、プラグインとして入れることもできる。

私が気に入っている細部がある。その翻訳の範囲は、意図的に薄く作られている。i18n が翻訳するのは、Hermes 自身が出力する固定の文案だけだ。インターフェース、承認時の表示、スラッシュコマンドへの返信、そういったものだ。Agent が生成した内容、ログ、エラー、ツールの出力は、全部英語のままだ。

なぜ全部は翻訳しないのか。翻訳はドリフト（ずれ）するもので、ドリフトは Agent の行動判断を汚染しかねないからだ。翻訳を「インターフェースの外殻」に制限し、「思考の内核」に触れない。これは抑制の効いた、プロフェッショナルな決定だ。

デスクトップ App の方はもっと遠くまで行っていて、完全な簡体字中国語の UI を備えている。チャットウィンドウ、サイドバー、設定、コマンドセンター、cron、プラットフォーム設定、Skill、profiles、UI 一式が全部翻訳されている。背後では中国語コミュニティの貢献者が推し進めている。英語が依然としてデフォルトだが、簡体字中国語は今や一級市民だ。

### この節で本当に変わったのは何か

3つの顔に ACP と簡体字中国語を加えて一緒に見ると、Hermes の受け手の裾野が大きく下がったことが分かる。

旧版の本では、これはギークのためのものだった。コマンドラインが分かり、VPS が設定でき、英語のエラーを読めなければならなかった。その敷居が、ほとんどの人を外に締め出した。

今は違う。公式の一文が急所を突いている。以前、友人に Hermes を薦めようとすると、相手の「目がだんだん虚ろになっていく」のを見なければならなかった。今はインストールパッケージをそのまま送って、ダブルクリックで動かしてもらえばいい。

これは技術のアップグレードではなく、受け手の拡張だ。自分で進化する同じ脳が、かつてはターミナルを打てる人にしか飼えなかった。今は普通の人にも手が届く。本を1冊書いて「Agent がどう賢くなるか」を語るなら、この節で1文補わなければならない。それは、誰でも使えるようになる努力もしている、ということだ。

次の Part では、視点を「あなたがどう使うか」から「それがどう他人を指揮するか」に切り替え、1つの Agent がどうやって Agent の群れをスケジューリングするかを見る。
