## §01 Hermes と出会う：自分でスキルを育てる Agent

まず本書の主役を紹介しよう。Hermes Agent は、オープンソースで、自己改善する AI Agent だ。あなたのことを覚えていて、積み重ねた経験から自分でスキルを書き、あなたが眠っている間もバックグラウンドで働き続ける。「ツール」と呼ぶと、むしろ小さく言いすぎになる。使えば使うほどあなたのことを分かってくれる、デジタルな同僚と言った方が近い。

### 実際に何ができるのか

いちばん普通の場面を思い浮かべてほしい。初めて使うときは、Telegram で一言メッセージを送るか、ターミナルでコマンドを打って、スクレイパーのスクリプトを書かせるくらいだろう。返ってくるものは動く。でも、スタイルはあなたの好みとは限らない。変数の名付け方、エラーの扱い方、ログの出し先。まだあなたのことを知らないので、無難な一般解に逃げるしかない。

ところが10回目ともなると、景色はまったく違う。あなたが `requests` より `httpx` を好むこと、ログはターミナルに流すよりファイルに書くのが好きなこと、長すぎる関数を嫌うこと。そういうことを全部知っている。誰かが教えたわけではない。以前のやり取りから自分で学び、自分のスキルライブラリに書き込んだのだ。

Hermes が特別なのはここで、一行で言える。世の中のたいていの Agent は、手綱（ハーネス）を人間が手作業で付けさせる。ルールを書き、権限を設定し、メモリを手入れする。Hermes は手綱を付けた状態で出荷されてくる。しかも大事なのは、その手綱が自分で育つことだ。

できることを全部並べると、だいたいこうなる。

| 能力 | 実際にどういうことか |
|---|---|
| あなたを覚える | セッションをまたぐ長期メモリ。あなたが誰で、何を好み、前回どこまで話したか、全部保持するので、毎回ゼロから説明し直さなくていい |
| 自分でスキルを書く | 得た経験が再利用できる Skill として定着する。次に似た仕事が来たらそれを呼ぶだけ。使うほど手際が良くなる |
| バックグラウンドで働く | 定時タスクを回せる。あなたが眠っている間に日報を回し、コードのパイプラインを見張り、長期プロジェクトに目を配る |
| Agent の一団を指揮する | 一つのメイン Agent がサブ Agent を生んで並行作業させ、自分は指揮者の席に座る |
| どこからでも届く | コマンドライン、ネイティブのデスクトップ App、ブラウザの管理パネル、20あまりのチャットプラットフォーム。どこでも同じ「それ」がいる |

だから「AI アシスタント」と呼ぶより、デジタルな同僚と呼びたい。あなたがいない間も働き続け、一緒に仕事をするほど呼吸が合ってくる同僚だ。本書が解剖していくのは、この同僚の脳がどう育ち、どうやって自分を賢くしていくかである。

### すでに知っているアレらと、どういう関係か

たぶん、いくつか名前を聞いたことがあるはずだ。Harness、Claude Code、OpenClaw。似たようなものに聞こえるので、読み進めて混乱する前に、まず座標系を置いておこう。

Harness は方法論であって、製品ではない。Harness Engineering の橙皮書を読んだ人なら覚えているだろう。AI Agent にどうやって「手綱を造る」か、という話だった。指示の層、制約の層、フィードバックの層、メモリの層、オーケストレーションの層。五つの構成要素からなる、一式の考え方だ。Harness 自体は、ダウンロードしてくるようなソフトウェアではない。

Hermes は、その考え方を製品にしたものだ。五組の手綱を全部付けた状態で出荷されるので、一つひとつ自分で設定しなくていい。さらに一歩進んで、手綱を「自分で育つインフラ」にしてしまった。ここがたいていの Agent とのいちばん根本的な違いで、本書の Part 3 の焦点でもある。

Claude Code と OpenClaw は同業だが、立ち位置が違う。大ざっぱに分けると、Claude Code は対話型のコーディングで、あなたが座ってコードを書くのを見ているもの。OpenClaw は「設定すなわち振る舞い」に寄っていて、ペルソナとルールを書けばその通りに動く。Hermes は「自律的なバックグラウンド動作＋自己改善」に重心を置く。三者は近づきつつあるが、出発点は違う。

### ついでに言うと、人気がちょっと異常なことになっている

何であるかは説明したので、外せない脱線を一つ。今、このプロジェクトの熱量は本当に高い。

GitHub の star は25万を超えた（2026年10月20日に私が確認した数字は 255,216。四か月前に前版を書いたときは18万を少し超えたところだった）。Dealroom の「2026年に最も速く成長しているオープンソース Agent フレームワーク」のリストにも入った。リポジトリを開くたびに、数字はまだ伸びている。

イテレーションの速さを感じる数字を一つ。前版の本が拠って立つ v0.16.0 は、リリースノートによれば800を超えるコミット、500を超える PR、170人を超えるコントリビュータでできていた。10月中旬の v0.22.0 では、公式の数字は v0.21.0 以来で約2万4千のコミット、6千を超える PR、2千5百人を超えるコントリビュータ。前のサイクルの2.5倍だ。6月5日から10月15日までの131日で24バージョン、平均して5日半に一つ出ている。

その速さは私自身、身をもって感じた。この本はもう第3版だ。4月に初版を書いたとき、Hermes はまだターミナルで動き、Telegram で遠隔操作するオタクのおもちゃだった。6月の第2版では、ネイティブのデスクトップ App、ブラウザの管理パネル、簡体字中国語への対応が生え、公式はあの版を "The Surface Release"（表の顔のリリース）と呼んだ。10月のこの版（v0.22、コードネーム "The Threshold Release"＝敷居のリリース）では、焦点が「敷居（しきい）」に移った。デスクトップ App の初回起動はガイド付きの対話になっていて、無料の試用モデルでそのまま動き始め、API キーは要らない。インストーラには署名が付き、Microsoft Store にも並んだ。ローカルモデルをワンクリックで走らせる機能まで付いた。一行で言えば、核はほとんど変わっていない。でも、コマンドラインの古参しか触れなかったものが、友人にインストーラを送ればダブルクリックで使える製品になったのだ。

はっきりさせておく。速いアップデートは表面にすぎず、本書の本題ではない。AI の世界では毎月、猛ダッシュする製品が出てくる。速いだけなら面白くない。Hermes に一冊まるごと割く価値があるのは、その速さの裏にある安定した核だ。自分で手綱を造る Agent、そして自分で育つ手綱。その話は後で少しずつしていく。

私自身の立ち位置も置いておこう。資料をかき集めて急ごしらえした本だと思われたくないので。この2年、私はほぼすべてを AI Agent とスキルに注いできた。オープンソースの女媧.skill は star が3万5千を超え、デザイン用の huashu-design は2万5千、自己進化する達爾文.skill は6千を超えた。この本の前版自体も、GitHub で5千近い star を集めている。自己改善する Agent と自己進化するスキルは、私が毎日触って、遊んでいるものだ。だから Hermes のこの半年の一歩一歩を、私は基本的に現場で見てきた。

### OpenClaw から引っ越すべきか

今 OpenClaw を使っている人は、この節だけ独立して読んでほしい。引っ越すかどうかに直結するかもしれないからだ。

今年、OpenClaw には大きな出来事があった。創業者の Peter Steinberger が OpenAI に加わると発表し、プロジェクト自体は非営利の財団に託された。規模だけ見れば、今でも OpenClaw の方が Hermes より大きい。だが差は縮んでいる。6月に前版を書いたとき、その star は Hermes のだいたい2倍だった。10月20日に改めて確認すると、39万対25.5万、だいたい1.5倍だ。

一方の Hermes 側は、なかなか面白い手を打った。「OpenClaw より俺の方が上だ」という言葉の殴り合いで止まらなかった。製品の中に、引っ越し当日の絨毯を敷いてしまったのだ。ソースコードの中に `hermes claw migrate` というコマンドがあり、README には OpenClaw からの引っ越し方を教える節が丸ごとある。ペルソナ設定、メモリ、ユーザープロファイル、カスタムスキル、コマンドの許可リスト、プラットフォームごとの設定、API キー。ローカルの OpenClaw ディレクトリを自動検出して、一気に全部持ってくる。その後には、もっと汎用的な `hermes import-agent` まで加わった。Claude Code や Codex CLI の設定を取り込めて、`--sync` を付ければ継続的に同期までできる。

> **核心的な助言**
>
> 引っ越すかどうか、私の助言は「結論を急ぐな」だ。本書の後半で Hermes のメモリ、スキル、セキュリティの仕組みを深く歩いていく。それを読んでから「引っ越す価値があるか」を決める方が、今ここで思いつきで当て推量するよりずっといい。ただ、一つだけ先に覚えておけることがある。引っ越しの技術的なコストを、Hermes はすでにほぼゼロまで押し下げた。そしてそれ自体が、一つのシグナルだ。

### 本書が連れて行くのは、顔の下にある核だ

だから本書は、この新しい顔がどれだけ見栄えがいいかを褒めることに、あまり紙面を使わない。オタクのおもちゃが大衆向けツールになる。そういう物語は珍しくない。

本当にあなたの時間に値するのは、顔の下にある核だ。自分で手綱を造り、その手綱が自分で育つ、自己改善する Agent。あなたがどういう人間かを覚え、経験から新しいスキルを書き、あなたが眠っている間に定時タスクを回す。デジタルな同僚のように。

Nous Research には「Hermes は内蔵の学習ループを持つ唯一の Agent だ」という公式の言い方がある。これは彼ら自身の主張で、引用するときは「公式の自己申告であって中立な結論ではない」と明記しなければならない。だが学習ループ自体は、すでに「アイデア」から、ソースコードの中で指させる「仕組み」になった。その部分は本物だ。

次節では60秒でパノラマを描く。一つの脳、たくさんの顔。それが一体どう組み合わさっているのか。その絵を見ておけば、この先読むどのサブシステムにも、掛ける場所ができる。

## §02 60秒全景：一つの脳、たくさんの顔

いくつもの製品を見ているように思えるだろう。コマンドライン、デスクトップ App、Web のダッシュボード、20あまりのチャットボット。だが、その下は実際には全部同じものだ。アーキテクチャ全体は一文に収まる。一つの脳、たくさんの顔。

### まずこの図から

Hermes のアーキテクチャを描くと、真ん中に AIAgent という孤独な円が一つある。その周りに箱の輪が座る。CLI、Ink で作られた TUI、Electron のデスクトップ App、ブラウザの管理パネル、それに20あまりの IM プラットフォームのアダプタ。どの箱からも、あの円に線が戻っている。

| | |
|---|---|
| CLI / Ink 製 TUI / デスクトップ App | → **AIAgent** ← |
| Web パネル / 20あまりの IM プラットフォーム | → **AIAgent** ← |

この図から持ち帰るべきことは全部で一文だけだ。外側の箱はどれも「もう一つの Hermes」ではない。同じ核に違う殻を被せたものだ。

Telegram で話しかけても、デスクトップ App で話しかけても、コマンドラインでコマンドを打っても、当たっているのは同じ AIAgent インスタンスの同じロジックだ。顔を替えても、脳は同じまま。

### その脳はどういう姿か

AIAgent クラスはシステム全体の中枢だ。目立つ特徴が一つある。コンストラクタが80を超えるパラメータを取る。私が数えたのは v0.22.2 の `AIAgent.__init__` で、86個。四か月前の v0.16.0 では67個で、今も増え続けている。

認証情報、ルーティング、各種のコールバック、セッションの文脈、予算、認証情報のプール……全部が一つのコンストラクタに詰め込まれている。コードを書いたことがある人なら誰でも眉をひそめるだろう。教科書では「ゴッドオブジェクト」と呼ばれる、やってはいけないことの典型例だ。メンテナたちも避けては通らない。ソースの中の `AGENTS.md` は、このプロジェクトの決まりごと全体を二つの不変条件に圧縮している。「Per-conversation prompt caching is sacred（会話ごとのプロンプトキャッシュは神聖不可侵）」と「The core is a narrow waist; capability lives at the edges（核は細い腰であり、能力は縁に宿る）」だ。

だが、これは意図してそう設計されている。なぜそのレッテルを貼られてでも分割しないのかは、後で話す。

この脳が外界に開いている口は二つだけだ。一つは `chat(message)`。一文を投げ入れれば返事が返る。乱暴なまでに単純だ。もう一つは `run_conversation()` で、こちらが完全なインターフェースで、最終的な返事と、そのターン全体のメッセージリストを返す。日常使う機能はすべて、最終的にはこの二つのメソッドに流れ込む。

内部では同期ループが回っている。今流行りの async ではない。割り込みチェック、予算の追跡、そして一度きりの猶予呼び出し（grace call）を備えている。モデルがツールを呼びたいと言えばツールを呼び、結果をメッセージリストに詰め戻して、もう一度モデルに聞く。モデルが話し終えたら、ループは終わる。周回の上限はこの数か月で三度変わった。以前はデフォルトで最大90周だったものが、v0.20 で500まで緩み、今はメイン Agent のデフォルトは上限なしだ（設定は `agent.max_turns: null`。上限があると長いタスクが途中で静かに切り捨てられる、とコメントに書かれている）。サブ Agent には別に250周の上限がある。

### 五つの内蔵システム、Harness の五要素への対応

Harness Engineering の橙皮書を読んだ人なら、手綱の枠組みを覚えているだろう。指示、制約、フィードバック、メモリ、オーケストレーション。当時の議論は「Agent にどう手綱を付けるべきか」だった。

Hermes の面白さは、その五要素の全部を、最初から内蔵システムとして出荷していることだ。あなたが設定して入れるのではない。最初から体の一部になっている。一対一で対応させるとこうなる。

| Harness の要素 | Hermes では何か | 一行で |
|---|---|---|
| 指示の層 | Skill システム | Markdown のスキルファイル。system prompt ではなく user message として注入される |
| 制約の層 | ツールセットの切り替え＋サンドボックス＋7種のターミナルバックエンド | 与えるべき権限は与え、触らせてはいけないものは締める |
| フィードバックの層 | 自己改善の学習ループ＋Curator | 使うほど良くなり、古びたスキルは自分で刈り込む |
| メモリの層 | SQLite＋FTS5＋差し替え可能なメモリプロバイダ | ローカルに保存し、全文索引を付け、セッションをまたいで見つけられる |
| オーケストレーションの層 | サブ Agent への委任＋定時タスク＋Kanban ボード | 一つの Agent が Agent の一団を指揮して仕事をさせる |

本書の後の章は、基本的にこの五行に沿って掘り下げていく。各行に、それぞれのソースコード、設計上のトレードオフ、落とし穴がある。この節は地図を広げるだけのもので、パズルの各ピースがだいたいどこにあるかを知ってもらうためのものだ。

この対応を覚えておいてほしい。本書全体の骨格だ。後でどこかのシステムがややこしく感じたら、この表に戻ってきて「これは手綱のどの要素だ？」と自問すれば、だいたい整理がつく。

### なぜゴッドオブジェクトを背負い、マイクロサービスに割らないのか

ここまで来れば、疑問が一つあるはずだ。60個のパラメータを呑み込むゴッドオブジェクトは、明らかに「優雅ではない」。この人たちは腕が悪くないのに、なぜ綺麗なマイクロサービスに割らないのか。

私も最初はそう思った。マンガー（Munger）の言葉がある。一見おかしな決定に出くわしたら、すぐ「あいつは馬鹿だ」と言わず、まず「そうすることで何を買ったのか」を問え、と。

買ったものは、とりわけ貴重なものだ。あらゆるプラットフォームで完全に一貫した振る舞いである。

すべての顔が同じ脳を共有しているから、デスクトップ App で調整した好み、教え込んだ習慣、覚えさせた事柄は、コマンドラインに移っても、Telegram に移っても、全部そこにある。「同期」されてくるのではない。文字通り同じものなので、突き合わせるべき状態のコピーが二つ存在しないのだ。マイクロサービスに割った瞬間、分散システムの古い問題一式に直面する。状態をどう同期するか、メッセージの一貫性をどう保つか、どのサービスが真実の源か。

そして、このトレードオフを本当に釘付けにしているのは、触れない二つの硬い制約だ。

> **推奨される側の事情 — プロンプトキャッシュを壊してはならない。**
> 会話の途中で、過去の文脈を変えてはならない。ツールセットを入れ替えてもいけない。system prompt を再構築してもいけない。一つ変えればキャッシュは丸ごと無効になり、リクエストのたびにトークンを燃やし直すことになる。Skill が system prompt ではなく user message として注入される理由でさえ、この制約だ。

> **推奨されない側の事情 — 何万ものテストは動かせない。**
> `def test_` で大ざっぱに数えてみたところ、v0.22.2 には4万6千を超えるテスト関数がある。アーキテクチャを作り替えることは土台を動かすことで、それらのテスト全部が巻き添えになる。工学的なコストは、現実的でないほど高い。

この二つの制約を並べれば、答えは明らかだ。これは本当に、技術的な趣味の問題ではない。工学的な現実主義だ。ゴッドオブジェクトで「全プラットフォームで一貫した振る舞い」が買え、それを引きはがす代償が「壊れたキャッシュ＋何万ものテストの書き直し」だとすれば、その重さを背負う方が賢い選択なのだ。

v0.15 から v0.16 にかけては、この抑制を裏付けるような、教科書的なリファクタリングが行われた。1ターンの会話を駆動する巨大なメソッド、ほぼ3,900行を、そっくり独立したモジュールへ移し、元の場所には薄い転送役だけを残した。そして何万ものテストが一つも壊れないよう、あえて間接参照の仕組みを使った。まず象を動かせるようにして、それから解体の話をする。再設計はしない。状態の形も変えない。ただ場所を移すだけだ。

面白いことに、後には本当に割った。v0.22 までに、メインファイル `run_agent.py` は5千3百行超から1千5百行超へ細り、Gateway のメインファイルは3万4千行超から5千5百行へ細った。公式によれば、コードベース全体は106万行から70万行あたりまで減り、19ほどの地味なツールがオンデマンド読み込みに変わった。順番は「まず動かし、それから割る」で、二つの段階の間にはいくつものバージョンが挟まっている。これが Hermes のアーキテクチャの性格だ。保守的で、実務的で、実際のコストへの敬意を持っている。

一つの脳、たくさんの顔。この一行は単なる比喩ではない。二つの硬い制約に押し出されて生まれた、考え抜かれた工学的な決定だ。次節では角度を変えて、Nous がこんなものを造って、一体何を狙っているのかを見ていく。

## §03 Nous はなぜこれを造ったのか

何かが無料で、オープンソースで、猛烈な勢いでイテレーションしているとき、あなたの最初の反応は感謝ではなく警戒であるべきだ。Hermes Agent はまさにそういうものだ。金を出している連中が何を狙っているかを見抜けば、それをどれだけ信用していいかが分かる。

### まず、耳の痛い問いから

Hermes Agent は MIT ライセンスで、ソースは全公開で、クローンして5ドルの VPS に載せれば、Nous に1セントも払わずに動く。半年で star は2万少しから25万を超えた。研究所が何十人もの人間と何万ものコミットを注ぎ込み、造り上げて、タダで配っている。彼らに何の得があるのか。

この問いは、どんな機能案内よりも大事だと私は思う。ツールの長期的な信用は、今どれだけ便利かでは決まらない。それを造る連中に、血を流し続ける理由があるかどうかで決まるのだ。情熱だけで回っているオープンソースは、作者が他で忙しくなった瞬間に止まる。利害の輪がはっきりしているプロジェクトの方が、長生きする傾向がある。だからこの節は機能の話をしない。Nous の算盤をはじくための節だ。

読み終える頃には、Hermes をタダで配ることが Nous にとって少しも損ではないことが分かるだろう。彼らが狙っているものは、三つの場所に隠れている。

### Nous とは誰か：力任せを信じない連中

Nous Research はオープンソースの AI 研究所で、中心人物は Teknium だ。Hermes のリリースはすべて彼の名前で出ている。この会社が名を上げたのは Hermes 系列のモデルで、初期の Nous-Hermes から Hermes 2、そして2025年の Hermes 4 へと、14B、70B、405B の三つのサイズでハイブリッドな推論モデルを出してきた。

その全部を一貫した信念が貫いていて、それが全体を理解する鍵だと私は思う。巨大な事前学習の予算は要らない。質の高い事後学習（post-training）があれば、小さなチームでもフロンティアに迫れる、という信念だ。

主流の物語はこうだ。計算資源を積み、データを積み、パラメータを積み、GPU を一番持っている者が勝つ。Nous はその話に乗らない。賭けているのは事後学習だ。ベースモデルを取り、綿密に設計したファインチューニングとアライメントのデータで、制御可能で、検閲に縛られず、ユーザーの言うことを本当に聞くモデルに仕上げる。この道がいちばん依存するのは何か。質の高い訓練データだ。とりわけ、モデルが道具を呼び、タスクを一歩ずつやり遂げていく、その過程のデータである。

下に述べる一つ目の動機は、まさにこの事後学習の路線から生えてくる。

### 動機一：それは Nous 自身の研究施設でもある

> **訳者注 — §03 の訂正（Errata）と本訳の翻訳元について**
>
> 英語版第2版（v260607）の原文では、この「動機一」は「Hermes Agent は利用者の実利用データを大規模に収集し、Nous 自社モデルの訓練に回す収穫機でもある」という推論として書かれていました。しかし著者 HuaShu 自身が、原リポジトリの README に Errata（訂正）を出し、この推論は**誤り**であると明言しています。根拠は次の通りです。公式 FAQ によれば、API 呼び出しは利用者が設定した LLM プロバイダにだけ送られ、Hermes Agent はテレメトリ・利用データ・分析データを収集せず、会話・メモリ・Skill はすべてローカルの `~/.hermes/` に保存されること。また公式の `AGENTS.md` は「利用者の明示的な opt-in なしの外部送信テレメトリ」を、出来が良くても却下されるコントリビューションとして挙げていること。つまり利用者の軌跡が Nous に送られる経路は存在しません。
>
> 本日本語訳は、中国語版第3版（v261020）を主たる翻訳元に切り替えたため、この §03 は第3版で既に訂正済みの本文を正本として訳しています（動機一の見出しも第3版の「それは Nous 自身の研究施設でもある」に従いました）。英語版ベースの初訳では訳者注で訂正を補っていましたが、現在の本文自体が著者の訂正を反映したものです。

Hermes のリポジトリのルートディレクトリを開くと、地味な大きなファイルが二つある。一つは `batch_runner.py`、もう一つは `trajectory_compressor.py` だ。やっているのは「軌跡（trajectory）」をバッチで生成し、それを圧縮すること。軌跡とは、Agent がタスクを渡されてから、どう考え、どのツールを呼び、どの落とし穴にはまり、最後にどう解いたか、その完全な記録のことだ。

README には "Research-ready" という節があり、用途がはっきり書かれている。この基盤は、次世代のツールを使うモデルを訓練するために造られている。

道具呼び出しのデータは、今もっとも造るのが難しい訓練コーパスの一種だ。静的なテキストではなく、動的な過程だからだ。「タスクが提起され、Agent が本当に API を呼び、本当に成功と失敗があった」という過程である。優れた Agent フレームワークがあれば、Nous と研究者は**自分たちの環境の中で**タスクをバッチで回し、この種の軌跡を生み出せる。

> 自分たちの環境でタスクをバッチ実行する → ツール呼び出しの軌跡 → 訓練データに圧縮する → 次世代モデルを訓練する

この鎖は、Nous と研究者自身の環境の中だけで回り、あなたのコンピュータを通らない。公式 FAQ がはっきり書いている通り、API 呼び出しはあなたが設定したモデルプロバイダにだけ送られ、Hermes Agent はテレメトリも利用データも分析データも収集しない。会話も、メモリも、Skill も、ローカルの `~/.hermes/` に保存される。公式の `AGENTS.md` に至っては、「利用者の明示的な opt-in なしの外部送信テレメトリ」を、却下されるコントリビューションとして挙げているほどだ。

### 動機二：オープンソースで人を集め、Portal で金を取る

研究上の使い道だけでは、会社のキャッシュフローは支えられない。二つ目の動機は、Nous がせっせと埋めつつあるビジネスモデルだ。

Hermes 自体は無料だが、初回インストールのときに、Nous Portal というものをデフォルトの推奨経路として押し出してくる。次の節（§04）で実際に目にする通り、`hermes setup` の最初の画面には三つの選択肢があり、先頭にあって recommended（推奨）と印が付いているのが「Quick Setup (Nous Portal)」だ。デスクトップ版の初回起動で使われるのも、Nous がくれる一回限りの無料試用モデルである。Portal は Nous のサブスクリプションサービスで、200から300のモデル（公式サイトのトップには 200+、ドキュメントには 300+ とあり、両者は揃っていない）に加え、Web 検索、画像生成、テキスト読み上げ、クラウドブラウザ、クラウドサンドボックスといった細々したものを一つに包むツールゲートウェイを束ねている。料金の段位もはっきりしている。無料枠があり、その上に月額20ドル、100ドル、200ドルの三段。ターミナルから `/subscription` や `/topup` でそのまま購読を管理できる。

オープンソースのマネタイズとしては古典的な手筋だが、運びが滑らかだ。

| この層 | 表向きは何か | 裏で狙っているもの |
|---|---|---|
| Hermes Agent | 無料のオープンソースツール、人を集める | 研究施設＋集客の漏斗（ファネル） |
| Nous Portal | 一括りのサブスクリプション、API の山と格闘しなくて済む | マネタイズの入口と、モデル配布の入口を自分の手に握る |
| Hermes モデル系列 | オープンでダウンロードできるフロンティアモデル | Portal 経由で配布される（ただし公式ドキュメント自身が、Hermes 4 系列は Hermes Agent を駆動する用途には勧めていない） |

オープンソースがユーザーの洪水を引き込み、Portal が、そのうち「金を払ってもいい、設定で煩わされたくない」という層を購読者に変える。もっと大事なのは、Portal が全員のデフォルトの入口になったとき、Nous はモデル配布の喉元を押さえるということだ。あなたは Hermes を使い、そのまま Nous のモデルとサブスクリプションを使う。

ここには、直感に反する細部が一つある。Portal の公式ドキュメントには、Hermes-4-70B と 405B は「Hermes Agent の中では使わない方がいい」と専用の段落で書かれている。チャットと推論向けに調整されていて、ツール呼び出しのループは得意ではないからだ。つまり少なくとも今のところ、この Agent を駆動する主力は他社のモデルであり、「自社モデルが Agent に血を戻す」という輪はまだ本当には閉じていない。

私が言えることの限界は、はっきりさせておく。Portal が実際にどれだけ転換し、どれだけの金を生んでいるかは、Nous は公開していないし、私にも一次データはない。私が述べているのは仕組みだけだ。「純粋なオープンソースツール」から「オープンソースツール＋自前の有料サブスクリプション」へ。Nous は明らかに、自分で血を流し続けられる道を造っている。その道が存在することの方が、それが今いくら稼いでいるかより大事だ。

### 動機三：ライバルが魂を失った。今が狩りのとき

最初の二つの動機は Nous 自身のエンジンだ。三つ目は外側のタイミングで、しかも一生に一度の窓だ。

Hermes の最大のライバルは OpenClaw、同じくオープンソースの個人 AI アシスタントで、Hermes より大きい（2026年10月20日時点で star は39万対25.5万、だいたい1.5倍。6月時点では2倍だった）。だが2026年2月、OpenClaw の創業者 Peter Steinberger が OpenAI に加わると発表し、プロジェクトを非営利の財団に委ねた。

それが何を意味するか。オープンソースプロジェクトの最大の資産は、たいていコードではない。趣味と方向感覚を持った、あの一人の人間だ。魂が去れば、どんな大きな盤面でも揺らぎ始める。ユーザーは本能的に思う。これから誰が舵を取るのか。移り先を探した方がいいのではないか、と。

Hermes はこの窓を正確に読んだ。一方では猛烈に出荷した。6月から10月までの131日で24バージョン。もう一方では、自分の製品の中に、OpenClaw から引っ越すための絨毯を敷いた。§01 で触れた `hermes claw migrate` で、古い設定を自動検出し、メモリとスキルを一気に移す。伝統的な競合とは、姿勢がかなり違う。

> **推奨される姿勢 — Hermes の姿勢。**
> 「ライバルより俺の方が優れている」と言うだけではない。「ライバル側から痛みなく引っ越す方法はこちら」を製品の中に書き込み、明示的な集客戦略にする。

> **推奨されない姿勢 — 伝統的な競合の姿勢。**
> ライバルより優れている点はここだ。向こう側からどうやって来るかは、自分で考えてくれ。

Nous の算盤に戻して見れば、この一手の動機は明らかだ。ライバルが代替わりし、成長が鈍るその隙間こそ、既存ユーザーを掴むコストがいちばん安い瞬間だ。移行の経路を先に敷いておくことは、相手側がいちばん迷っているその瞬間に、「こちらへどうぞ」の地図を差し出すようなものだ。

### 三つの動機を重ねて、どれだけ信用すべきか

三つを積み上げれば、Nous の算盤は明らかになる。無料のオープンソースで最も多くの実ユーザーを引き込み、Agent フレームワークを自分たちの環境で回して訓練用の軌跡を造り、Portal で金を払うユーザーを掴み、ライバルが代替わりする隙を突いて最大の市場シェアを取る。各リンクが次のリンクに血を送り、全部が噛み合っている。

では、この節の頭に置いた耳の痛い問いに戻ろう。Nous が何を狙っているか分かった今、どれだけ信用すべきか。

私の見立てはこうだ。企みがはっきりしているからこそ、かえって信用できる。恐れるべきは、何で食っているのか説明できず、情熱のほとばしりだけで走っている類のプロジェクトだ。情熱が冷めれば未完で終わる。Nous には研究上の使い道があり、ビジネスの輪があり、市場を掴む明確な動機がある。つまり Hermes を長期に造り続ける強い理由があるということだ。利害の一致したオープンソースは、感情で駆動されるオープンソースより遠くまで行く傾向がある。

> **核心的な助言**
>
> 「無料で便利な」オープンソースツールについては、まず問う価値がある。それを造る連中は、何で食っているのか。答えがはっきりしているほど、そのプロジェクトは長期の賭けに値する。答えが曖昧なほど、いつ止まってもいいように心の準備をしておくべきだ。Hermes は前者で、それが私が一冊かけてこれを解剖しようと思う理由でもある。

動機の層はここまでだ。次の Part では、原理に急いで入る前に、まず Hermes をインストールして、実際に一度使ってみる。
